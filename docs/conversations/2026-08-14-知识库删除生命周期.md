# 知识库删除生命周期

## 背景

之前删除知识库只删除数据库记录。数据库级联关系可以清理文档、任务、chunk 和会话，但上传目录中的原始文件不会自动消失；检索缓存也可能短时间保留已经不存在的知识库结果。

## 已确认结论

- 删除入口仍是 `DELETE /api/knowledge-bases/{id}`。
- 只有当前管理员拥有的知识库才能删除。
- `pending` 或 `processing` 文档任务存在时返回 `409`，避免 Worker 与破坏性删除同时操作。
- 数据库事务提交后，再清理本地源文件并使该知识库的检索缓存失效。
- 数据库删除和文件删除不是一个原子事务：文件清理失败只记录结构化后端日志，不恢复已经提交的数据库记录。
- 前端提供确认弹窗、删除中状态和 409 错误提示；本轮浏览器验证不点击真实删除，避免误删现有资料。

## 实现链路

`Handler → knowledgebase.Service → PostgresStore.DeleteWithFiles → 文件清理/检索缓存失效`

`DeleteWithFiles` 在事务中读取源文件路径、锁定文档和活动任务、执行知识库删除；`Service` 负责协调数据库之外的文件系统和缓存能力。原有 `Store.Delete` 接口保留，便于旧调用方兼容。

## 验证结果

- Go 知识库、Handler 和 App 包测试通过。
- 前端构建和真实浏览器页面检查通过；未执行真实知识库删除。

## 后续待办

- 如果未来支持对象存储，需要把本地 `FileStore` 换成带批量删除和重试语义的存储适配器。
- 如果部署多实例，需要把检索缓存失效扩展为跨实例通知或共享缓存策略。
