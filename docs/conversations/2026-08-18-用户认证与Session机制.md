# 用户认证与 Session 机制

## 用户提问记录

- Session 是什么？从登录开始是怎么工作的？
- Session 每次都要携带 Session ID，为什么不直接携带用户名和密码？
- bcrypt 为什么不可逆？
- 用户功能和用户级记忆应该如何设计？

## 核心结论

Session 不是密码，也不是可解密的数据，而是登录成功后服务端签发的临时凭证。

```text
用户提交邮箱和密码
    ↓
服务端使用 bcrypt 校验密码
    ↓
生成随机 Session Token
    ↓
数据库保存 Token 的哈希、user_id 和过期时间
    ↓
浏览器通过 HttpOnly Cookie 保存原始 Token
```

后续请求不再发送密码，只发送 Session Cookie。服务端对 Cookie 中的 Token 再做哈希，查询 Session 表，确认它属于哪个用户、是否过期、是否被撤销，然后把当前用户写入请求 Context。

## bcrypt 为什么不可逆

bcrypt 是密码哈希，不是可逆加密。哈希会把输入压缩成固定长度结果，过程中会丢失信息，因此没有可用的反函数。

登录时不是解密数据库内容，而是重新计算：

```text
用户输入密码 + 哈希中保存的 salt
    ↓
bcrypt
    ↓
和数据库中的哈希比较
```

bcrypt 字符串中通常包含算法版本、cost、salt 和最终结果。算法公开不代表可以反向计算；攻击者只能不断猜密码并比较结果，因此需要使用 bcrypt/Argon2 这类故意较慢的密码哈希算法。

## Session 相比每次携带密码的优势

如果每次请求都携带用户名和密码：

- 密码出现频率更高，更容易进入日志、代理或错误记录。
- 无法只撤销某一个设备的登录状态。
- 密码泄露后会影响所有设备和所有请求。
- 每次请求都需要进行密码验证。

Session 的优势是可撤销、可过期、可区分设备，并且只在登录时验证一次密码。

```text
密码：身份证原件
Session：登录后发放的临时房卡
```

## 当前项目的实现

当前实现包含：

- `app_users`：保存邮箱和 bcrypt 密码哈希。
- `app_sessions`：保存 `user_id`、Session Token 哈希、过期时间和撤销时间。
- `POST /api/auth/register`：注册用户。
- `POST /api/auth/login`：验证密码并设置 HttpOnly Cookie。
- `POST /api/auth/logout`：撤销当前 Session 并清理 Cookie。
- `GET /api/auth/me`：返回当前登录用户。
- 认证中间件：解析 Cookie，把当前用户写入 `request.Context`。

当前 Cookie 使用 `HttpOnly` 和 `SameSite=Lax`；生产环境通过 `SECURE_COOKIES=true` 开启 `Secure`。

## 用户级记忆的关系

用户认证完成后，记忆数据不能只按知识库隔离，必须带上 `user_id`：

```sql
SELECT * FROM agent_memories
WHERE user_id = $1
  AND knowledge_base_id = $2;
```

删除记忆也必须同时带 `user_id`，否则用户可能通过猜测记忆 ID 访问或删除其他用户的数据。

## 面试表达

### Session 的完整流程是什么？

用户登录时提交密码，服务端用 bcrypt 校验；校验成功后生成随机 Session Token，只把 Token 的哈希保存到数据库，并通过 HttpOnly Cookie 把原始 Token 返回浏览器。之后每次请求由中间件验证 Token，查询出 user_id 并写入请求上下文，业务层根据 user_id 做数据权限过滤。

### 为什么不每次发送用户名和密码？

因为密码是长期高敏感凭据，出现次数越少越安全。Session 是可过期、可撤销、可按设备管理的短期凭证，能把密码验证限制在登录阶段。

### Session 和 JWT 有什么区别？

Session 的状态保存在服务端，适合需要立即注销、踢下线和权限实时变化的单体应用。JWT 通常把状态放在客户端，分布式验证方便，但撤销和权限变化更复杂。当前项目使用服务端 Session。

## 安全注意事项

- 不保存明文密码。
- 不把 Session Token 明文保存到数据库。
- Cookie 设置 `HttpOnly`、`SameSite`，生产环境使用 `Secure`。
- Session 必须有过期时间，并支持服务端撤销。
- 所有业务查询和删除都必须带当前 `user_id`。
- 登录接口需要增加限流，防止暴力破解。
- 注册和登录错误提示要避免泄露账号是否存在。
- 真正启用多用户前，必须完成旧知识库、会话、文档接口的用户权限迁移。
