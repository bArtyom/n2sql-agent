# 文档正文读取与预览

## 目标

`knowledge_search` 只返回与问题相关的片段，`document_list`/`document_info` 只返回目录和元数据。为了支持用户查看某个文档的正文，新增一个受限的 `document_read` 能力。

## 后端链路

1. `documentchunk.RangeReader.ReadRange` 按知识库、文档 ID、起始 chunk 和数量查询。
2. PostgreSQL 查询同时检查当前管理员和知识库归属，不接受文件路径。
3. 读取结果最多返回有限 chunk，并受字节上限约束；超过范围时返回 `next_position` 和 `truncated`。
4. Agent Service 创建知识库范围内的 `document_read` 工具，模型可以分段读取，不会一次获取整篇文档。
5. 新增 `GET /api/knowledge-bases/{id}/documents/{documentID}/preview`，前端文档列表的“查看”按钮使用该接口。

## 与现有能力的关系

- `knowledge_search`：不知道具体文档时，按问题找相关证据。
- `document_list`：知道知识库里有哪些文档。
- `document_info`：查看某个文档的类型、大小和处理状态。
- `document_read`：已经知道文档 ID 后，按片段范围读取正文。

## 边界注意

- 只读取数据库中已处理的 chunk，不直接读取本地任意路径。
- 知识库和管理员校验在 SQL 层完成；工具的知识库 ID由服务端绑定，不由模型传入。
- `limit`、起始位置和最大字节数都有上限；前端只显示有限窗口。
- 没有新增表或迁移，旧的 `documentchunk.Reader` 实现仍可通过逐块读取兼容。

## 为什么不能只依赖检索

`knowledge_search` 是“按问题找证据”：它返回相似度、关键词和融合排序靠前的少量 chunk，适合普通问答，但它是有损的相关性召回，不保证返回文档的连续内容，也不适合回答目录、状态和精确原文问题。

因此工具职责分开：

- `knowledge_search`：用户问“这个系统怎么部署”，根据问题找最相关片段；
- `document_list`：用户问“知识库里有哪些文件”，读取文档目录，而不是猜测搜索结果；
- `document_info`：用户问某个文档大小、类型或处理状态，读取确定的元数据；
- `document_read`：用户明确指定文档并要求查看正文、原文或连续段落时，按位置读取有限 chunk。

例如一个文档有 100 个 chunk，搜索“部署方式”可能只返回第 72、73 段；如果用户接着说“把这个文档开头三段原文给我”，再次用语义搜索不一定找到第 0、1、2 段，此时 `document_read(document_id, start_position=0)` 才是确定性读取。

`document_read` 读取的是数据库里已经处理的 chunk，不是任意本地文件，也不是把整篇原始文件塞入模型。当前回答引用仍主要由 `knowledge_search` 的 `sources` 产生；如果未来要求“正文读取结果也必须生成引用卡片”，需要再把读取 chunk 转成受限的 source 元数据。

## 后续补齐：正文读取也进入引用链路

已将 `document_read` 返回的有界 chunk 转换为统一的 `sources` 元数据，沿用 `tool_finished → sourceCollector → Response.Sources → conversation metadata → 前端引用卡片` 链路。它的 `matchType` 为 `document_read`，前端显示“按位置读取”和“指定片段”，不把距离 `0` 误显示成相似度分数。

前端正文预览现在支持“继续读取”：第一次请求从第 0 段读取 8 个 chunk，后续请求使用上一次响应的 `nextPosition` 作为 `start`，把新页面追加到当前窗口；每次请求仍受后端数量和字节上限保护。

## 问题建议的最小版本

问答台增加了三条起步问题和三条回答后继续追问。它们是前端固定模板，点击后直接复用现有 `askQuestion` 流程，不新增模型调用、接口或数据库字段。这样先解决“用户不知道如何开始”的体验问题；模型生成式建议和建议点击统计留到后续有明确收益时再做。

后续已补充按需生成入口：用户点击“生成更具体的追问”后，前端调用 `POST /api/knowledge-bases/{id}/follow-up-suggestions`，后端用当前聊天模型生成最多 3 条 JSON 建议。默认回答流程不会调用该接口；问题和回答会做长度限制、密钥样式脱敏，并把模型输出校验为有限的 `text/category` 结构。
