# Agent 节点循环与审批中断恢复

## 学习问题

Agent 的 ReAct 节点如何循环转移？工具需要用户审批时，Worker 中断后如何回到原来的工具调用位置？

## 核心结论

当前 Agent 是一个带循环的 ReAct 状态机：

```text
model
  ├── 没有 tool_calls → finish
  └── 有 tool_calls → tool
                         ├── 工具成功 → model
                         ├── 需要审批 → interrupt
                         └── 等待子 Agent → interrupt
```

`model` 负责让模型决定下一步，`tool` 负责执行模型已经决定的工具，`interrupt` 表示暂时暂停，`finish` 表示得到最终回答。`model → tool → model` 可以重复多轮，因此它不是单向 DAG，而是状态机循环。

## 普通工具调用

用户提问：

```text
用户：年假怎么计算？
```

模型先返回：

```json
{
  "tool_calls": [
    {
      "id": "call-1",
      "name": "knowledge_search",
      "arguments": "{\"query\":\"年假怎么计算\"}"
    }
  ]
}
```

Engine 把 assistant 的工具调用和待执行工具保存到 checkpoint：

```json
{
  "current_node": "tool",
  "messages": [
    {"role": "user", "content": "年假怎么计算？"},
    {"role": "assistant", "tool_calls": [{"id": "call-1", "name": "knowledge_search"}]}
  ],
  "pending_tool_calls": [
    {"id": "call-1", "name": "knowledge_search"}
  ]
}
```

工具返回结果后，Agent 追加 `role=tool` 消息，清除 `pending_tool_calls`，并将节点推进回 `model`。模型读取工具结果后，如果不再返回工具调用，就进入 `finish`，保存最终答案。

## 审批中断

假设模型决定调用有副作用的工具：

```json
{
  "id": "call-9",
  "name": "write_file",
  "arguments": "{\"path\":\"report.md\",\"content\":\"...\"}"
}
```

Engine 在执行前保存统一 checkpoint：

```json
{
  "current_node": "interrupt",
  "pending_tool_calls": [
    {
      "id": "call-9",
      "name": "write_file",
      "arguments": "{\"path\":\"report.md\",\"content\":\"...\"}"
    }
  ],
  "interrupt": {
    "kind": "approval",
    "id": "run-1:approval:call-9",
    "tool_call_id": "call-9",
    "tool_name": "write_file",
    "arguments": "{\"path\":\"report.md\",\"content\":\"...\"}"
  }
}
```

随后发布 `approval_required` 事件。持久化 Worker 返回 `ErrAgentApprovalPending`，Runner 调用 `MarkWaitingApproval`：

```text
agent_runs.status: running → waiting_approval
lease_token: 清空
lease_until: 清空
heartbeat_at: 清空
```

Worker 释放租约，不会一直占用 goroutine 等待用户点击。

## 用户批准后的恢复

前端提交：

```http
POST /api/knowledge-bases/1/agent-runs/run-1/approval
Content-Type: application/json

{"approved":true}
```

`ResolveApproval` 在一个 PostgreSQL 事务中：

1. 锁定 `agent_runs`，确认状态仍是 `waiting_approval`。
2. 锁定最新的统一 checkpoint。
3. 删除 `interrupt`。
4. 把 `call-9` 加入 `approved_tool_call_ids`。
5. 增加 checkpoint `version`。
6. 把 Run 状态改回 `pending`，清空旧租约。

之后任意 Worker 都可以领取原来的 `run_id=run-1`：

```text
run_id：不变
conversation_id：不变
attempt_count：增加
execution_id：重新生成
lease_token：重新生成
```

新 Worker 读取 checkpoint，发现：

```text
pending_tool_calls = call-9
approved_tool_call_ids = [call-9]
```

因此把 `call-9` 当作模型已经完成的决定，跳过再次调用模型，直接执行原来的 `write_file`：

```text
interrupt → tool → model → finish
```

工具完成后保存 `role=tool` 的结果，回到 `model`；模型可以根据写入结果生成最终答案。

## 用户拒绝后的恢复

如果用户提交：

```json
{"approved":false}
```

后端把 `call-9` 加入 `rejected_tool_call_ids`，删除 `interrupt`，并重新排队。Worker 接管后不会执行 `write_file`，而是向模型加入一条工具观察结果：

```json
{
  "role": "tool",
  "tool_call_id": "call-9",
  "content": "用户拒绝了这个工具调用，本次不会执行。"
}
```

此时逻辑路径是：

```text
interrupt → model
```

模型可以重新规划，例如改为直接回答，或者调用不需要审批的只读工具。

## 恢复信息的分工

```text
current_node：粗粒度位置，表示 model/tool/interrupt/finish
pending_tool_calls：精确指出还没有处理完的工具调用
interrupt：暂停原因和审批详情
approved_tool_call_ids：哪些工具已经允许执行
rejected_tool_call_ids：哪些工具已经被拒绝
messages：模型继续执行所需的消息协议
```

因此审批恢复不是依赖某一个字段，而是依赖同一个 `run_id` 下的统一 checkpoint。普通会话的 `conversation_id` 仍然不变，也不会因为一次审批恢复而创建新的聊天轮次。

## 设计原则

- 同一个 Run 崩溃恢复时，必须保留 assistant 的 `tool_calls`、工具结果、`pending_tool_calls` 和 `interrupt`。
- 审批决策应该和 checkpoint 更新、Run 重新排队放在同一个事务里，避免出现“已经批准但任务没有重新排队”的半完成状态。
- 跳过重新调用模型只能减少重复决策，不能单独保证副作用工具的 exactly-once；`write_file`、支付、发消息等工具仍应使用幂等键或外部操作 ID。
- 普通会话历史只保存用户消息和助手最终回答，与同一个 Run 的恢复上下文是两个读取场景，不能混为一谈。
