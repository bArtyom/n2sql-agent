# A2A 任务持久化设计

## 背景

当前 A2A 已支持 Agent Card、任务创建、状态查询和结果查询。任务保存在 `internal/a2a` 的进程内 map 中，由 goroutine 调用现有 Multi-Agent Supervisor。

当前实现适合演示，但有两个限制：

- 服务重启后，任务和结果全部丢失；
- 多实例部署时，不同进程无法共享任务，也无法可靠避免重复执行。

## 目标

第一版持久化只解决：

1. 任务和最终结果可在服务重启后查询；
2. `submitted` 任务可以在启动后继续执行；
3. 执行中的任务有租约，进程异常后可以恢复；
4. 保留现有 A2A HTTP 接口，不把数据库细节暴露给调用方；
5. 不引入 Redis、消息队列或完整 A2A 扩展。

第一版暂不做自动重试。模型调用重试会再次消耗 token，失败后先记录为 `failed`，由调用方重新创建任务。后续有明确指标后再增加有限重试。

## 存储选型

### 内存 map

优点是代码简单、延迟低；缺点是重启丢失、无法多实例共享，也无法恢复 `working` 任务。

保留为单元测试替身，不作为生产任务存储。

### PostgreSQL（推荐第一版）

项目已经使用 PostgreSQL、已有迁移机制和文档 Worker 任务表，可以复用事务、索引和 `FOR UPDATE SKIP LOCKED`。不需要增加新的基础设施，最符合当前项目范围。

### Redis

适合高吞吐队列和短生命周期任务，但会增加部署、数据恢复和一致性问题。当前 A2A 任务量没有证明需要 Redis，因此后置。

结论：先使用 PostgreSQL，保留 `TaskStore` 接口，未来可以替换 Redis，而不改 Handler 和 Supervisor。

## 表设计草案

表名建议：`a2a_tasks`。不要复用 `document_processing_tasks`，因为文档任务处理文件和向量化，A2A 任务执行 Agent；两者的输入、结果、失败恢复和权限都不同。

```sql
CREATE TABLE a2a_tasks (
    id TEXT PRIMARY KEY,
    administrator_id BIGINT NOT NULL REFERENCES administrators (id),
    knowledge_base_id BIGINT NOT NULL REFERENCES knowledge_bases (id),
    message TEXT NOT NULL,
    top_k INTEGER NOT NULL CHECK (top_k BETWEEN 1 AND 20),
    status TEXT NOT NULL CHECK (status IN ('submitted', 'working', 'completed', 'failed')),
    response JSONB,
    error_code TEXT,
    attempt_count INTEGER NOT NULL DEFAULT 0 CHECK (attempt_count >= 0),
    lease_until TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    started_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

字段作用：

- `id`：对外返回的任务 ID；
- `administrator_id`：记录任务所属管理员，避免任务查询跨管理员；
- `knowledge_base_id`：任务使用的知识库；创建时必须校验归属；
- `message`、`top_k`：恢复任务所需的最小输入；
- `status`：任务生命周期；
- `response`：成功后的结构化 Multi-Agent 响应，包含答案、引用和步骤；
- `error_code`：只存公开错误类别，如 `task_execution_failed`，不存 provider 原始错误；
- `attempt_count`：为未来有限重试保留；
- `lease_until`：Worker 租约，超过后可恢复卡住的 `working` 任务；
- 时间字段：用于状态查询、耗时统计和故障排查。

索引建议：

```sql
CREATE INDEX a2a_tasks_claim_idx
    ON a2a_tasks (status, lease_until, created_at);

CREATE INDEX a2a_tasks_knowledge_base_idx
    ON a2a_tasks (knowledge_base_id, created_at DESC);
```

第一版不保存模型 API Key、完整请求头、原始 provider 响应或内部堆栈。

## 状态流转

```text
submitted
    ↓ 事务领取
working
   ├─ 正常完成 → completed
   └─ 执行失败 → failed
```

进程异常时：

```text
working + lease_until < now
    ↓ 启动恢复/下一次领取
submitted
    ↓
working
```

这样不会让任务永久停在 `working`。

## 代码分层

```text
internal/a2a/handler.go
    负责 HTTP、JSON、状态码，不直接写 SQL

internal/a2a/store.go
    定义 TaskStore 接口

internal/a2a/postgres_store.go
    实现创建、查询、领取、完成、失败和恢复

internal/a2a/runner.go
    定时领取任务，调用 multiagent.Answer，更新任务状态

internal/multiagent
    只负责 Researcher → Answerer，不关心任务存储
```

推荐接口：

```go
type TaskStore interface {
    Create(context.Context, CreateInput) (Task, error)
    Get(context.Context, string) (Task, error)
    ClaimNext(context.Context, time.Duration) (Task, error)
    MarkCompleted(context.Context, string, multiagent.Response) error
    MarkFailed(context.Context, string, string) error
    RecoverExpired(context.Context) (int, error)
}
```

`Handler` 创建任务后只调用 `Create`；后台 `Runner` 负责领取和执行。这样 HTTP 请求结束后，任务仍然由 Runner 管理。

## 领取事务

核心思路与现有文档 Worker 类似：

```sql
SELECT id
FROM a2a_tasks
WHERE status = 'submitted'
   OR (status = 'working' AND lease_until < CURRENT_TIMESTAMP)
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

选中后在同一个事务内更新：

```sql
UPDATE a2a_tasks
SET status = 'working',
    attempt_count = attempt_count + 1,
    lease_until = CURRENT_TIMESTAMP + INTERVAL '10 minutes',
    started_at = COALESCE(started_at, CURRENT_TIMESTAMP),
    updated_at = CURRENT_TIMESTAMP
WHERE id = $1;
```

`SKIP LOCKED` 保证多个 Runner 不会同时领取同一条任务。

## HTTP 行为保持不变

```text
POST /api/a2a/tasks
    → 202 + {id, status: submitted}

GET /api/a2a/tasks/{id}
    → 任务状态和时间

GET /api/a2a/tasks/{id}/result
    → working 时返回 202
    → completed 时返回答案、引用和步骤
    → failed 时返回通用错误类别
```

查询任务时必须同时校验当前管理员和任务的 `administrator_id`，不能只根据任务 ID 返回数据。

## 与现有内存实现的迁移顺序

1. 先定义 `TaskStore`，让当前内存 map 实现它；
2. 将 Handler 从直接写 map 改为调用 `TaskStore`；
3. 增加 PostgreSQL migration 和 `PostgresTaskStore`；
4. 增加 Runner，替代每个请求启动 goroutine；
5. 启动时恢复过期 `working` 任务；
6. 保留内存 Store 测试，增加 PostgreSQL 集成测试；
7. 增加终态任务清理，最后再删除或保留内存实现作为测试替身。

## 观测与清理

沿用现有 A2A metrics：

- submitted、started、completed、failed；
- 任务终态耗时；
- claim 失败、恢复数量；
- 当前 working 数量。

日志继续只记录：`task_id`、`knowledge_base_id`、`status`、`duration_ms` 和公开错误类别。

已增加完成/失败任务 TTL 清理：默认保留 7 天，每小时执行一次；只删除当前管理员的终态任务，不删除 submitted/working 任务。

## 新增长期开发约定（2026-08-12）

- 后续 Go 代码优先采用惯用、直白、适合初学者阅读的写法：命名清楚、控制流自然、函数职责单一。
- HTTP、业务、存储和调度保持清晰分层；不同频率或生命周期的后台任务独立调度，避免把任务轮询和低频清理隐式耦合在一个时间判断中。
- 每个小功能交付时，补充最小 Go 示例和从入口到调用链的语法解释，帮助学习和复写。
