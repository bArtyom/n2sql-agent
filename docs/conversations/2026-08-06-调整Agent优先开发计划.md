# 调整 Agent 优先开发计划

## 背景

第一阶段知识库问答底座已经完成：文档上传、异步处理、文本切分、向量化、知识库检索、RAG/SSE 问答和最小 OCR 接入均已具备。当前 Worker 和 PostgreSQL 任务表保留作为文档处理底座。

## 已确认结论

- 下一步优先构建 Agent，而不是先引入 Redis、复杂重试或完整性能工程。
- 用户确认先完成 Agent 最小闭环，再逐步丰富能力；后续扩展必须建立在可运行、可测试的核心链路之上。
- Agent 先围绕现有知识库问答实现最小闭环：工具注册、知识库检索工具、Function Calling、ReAct、SSE 事件。
- 只补齐 Agent 当前需要的取消、超时、错误预算和事件边界；不为了“工程化完整”提前扩大基础设施范围。
- Redis、队列重试/退避/死信、指标、pprof 和压测后置到 Agent 主链路稳定后的阶段。
- 后续再做上下文/记忆/安全、Multi-Agent、MCP 和最小 A2A。

## Agent Runtime 小切片完成

- 参考 WeKnora 的 `AgentState`、`AgentStep` 和事件类型，将其缩小为 `AgentRun`、`Step`、`Event` 三个本地模型。
- `AgentRun` 支持 `pending → running → succeeded/failed/canceled` 生命周期，并拒绝非法状态转换。
- `Step` 支持模型决策、工具调用和最终回答三类步骤，自动分配稳定的顺序编号。
- `Event` 支持运行开始、步骤开始、工具调用、工具完成、消息增量和运行结束/失败/取消等事件类型。
- 未接入真实模型、HTTP、SSE 或 SQL/schema；下一步是实现 `KnowledgeSearchTool` 适配器。
- 验证通过：`go test ./...`、`go vet ./...`、`go test -race ./internal/agent`。

## KnowledgeSearchTool 小切片完成

- 新增 `KnowledgeSearchTool`，复用 `retrieval.Searcher`，不重复实现 Embedding 或 pgvector 查询。
- `Call` 负责解析 `knowledge_base_id`、`query`、`limit`，裁剪 query，补默认结果数并校验最大结果数。
- 检索结果以 JSON 文本放入 `ToolResult.Content`，保留文档名、位置、正文和距离等信息。
- 覆盖成功调用、非法 JSON、缺少知识库 ID、空 query、负数/超限 limit、检索失败和依赖缺失。
- 当前尚未在生产组装入口注册工具，也未加入 Function Calling 参数 schema；这两项属于下一小切片。

## Tool Definition 与注册组装小切片完成

- 当前仍未接入真实模型请求；下一步是把这些 Function Definitions 放入模型请求，并解析模型返回的 Tool Call。

## Function Calling 传输边界小切片完成

- `modelclient.ChatRequest` 现在可以携带 OpenAI 兼容的 `tools` 定义，工具定义由外层 `type=function` 和内层函数名称、描述、JSON Schema 组成。
- `modelclient.ChatResponse` 和 `ChatMessage` 支持 `tool_calls`、`tool_call_id`，允许模型返回“暂时没有文本、先调用工具”的响应。
- `HTTPClient.Chat` 会解析工具调用的 ID、函数名和 JSON 参数字符串，并继续拒绝既没有文本也没有工具调用的无效响应。
- 对模型返回的 Tool Call 会校验 ID、函数类型、函数名和对象参数；工具定义必须携带对象 JSON Schema。当前 `ChatStream` 明确拒绝工具调用，避免把流式工具增量静默丢弃。
- `modelruntime.ChatService.ChatMessagesWithTools` 将 Agent 的 `FunctionDefinition` 转换成模型客户端的工具定义，复用现有 provider、API Key 和错误包装逻辑。
- 已通过 `go test ./internal/modelclient` 与 `go test ./internal/modelruntime`；下一步是根据 `ToolCall` 查找 `ToolRegistry`、执行工具，并把工具结果作为下一轮消息回传给模型，形成最小非流式 ReAct 循环。

## Function Calling 代码讲解要点

- `agent.Tool` 是工具实现契约：`Name` 给模型识别、`Description` 给模型理解、`Parameters` 提供 JSON Schema、`Call` 执行真实业务。
- `KnowledgeSearchTool` 通过 `retrieval.Searcher` 复用现有检索能力；模型只看到工具描述和参数，不直接接触数据库或 Go 实现。
- `ToolRegistry` 保存真实工具实例；`FunctionDefinitions()` 只导出给模型的描述，`Find()` 留给后续执行 Tool Call。
- `modelruntime.ChatService.ChatMessagesWithTools` 负责 provider/API Key 和 Agent 定义到 OpenAI 兼容 `tools` 外层结构的转换。
- 当前代码已完成“定义工具 → 发给模型 → 解析 Tool Call”，尚未完成“按名称查 Registry → 执行 `Call` → 追加 tool 消息 → 再请求模型”的完整闭环。

## 最小非流式 Agent 执行器小切片完成

- 新增 `internal/agentruntime`，避免 `internal/agent` 与 `internal/modelruntime` 互相依赖形成循环。
- `Engine` 负责启动 `AgentRun`、向模型发送工具定义、解析 Tool Call、通过 Registry 查找并执行工具、追加 assistant/tool 消息并继续下一轮。
- 当前按顺序执行同一轮中的多个工具调用；未知工具、非法调用、空工具结果、模型错误会让 Run 失败。
- 以最大模型轮次限制循环，并处理上下文取消/超时；暂不接入 SSE、并行工具和 HTTP 路由。
- 补充了助手 Tool Call 消息的 `content: null` 序列化，兼容 OpenAI 风格的第二轮请求。
- 验证通过：`go test ./...`、`go vet ./...` 和 `internal/agentruntime`/相关包的 race 测试。

## Agent 问答入口接入小切片完成

- `KnowledgeSearchTool` 新增请求级知识库范围；Agent 场景下工具 Schema 不再让模型填写 `knowledge_base_id`，而是由 URL 中的 `{id}` 固定注入，避免跨知识库搜索。
- 新增 `internal/agentservice`，负责创建 scoped ToolRegistry、构造系统提示和消息、生成 Run ID，并调用 `agentruntime.Engine`。
- 新增非流式接口 `POST /api/knowledge-bases/{id}/agent-chat`，返回答案、Run ID、状态和步骤；原有 `/chat` 与 `/chat/stream` 保持不变。
- 新增 `AGENT_MAX_STEPS` 配置，默认 4，限制每次请求的模型/工具循环轮次。
- scoped 工具执行时使用 `DisallowUnknownFields` 严格校验参数，`additionalProperties:false` 不再只是模型提示；传入知识库 ID 等未知字段会被拒绝。
- 当前仍未接入 Agent SSE 事件、并行工具和记忆；下一步是把 Agent Run 的事件映射到已有 SSE 通道，再进行真实 API Key 的端到端验证。

## 请求级 scoped 工具的设计说明

- `agentservice.Service.Answer` 每个 HTTP 请求创建一次绑定当前知识库 ID 的 `KnowledgeSearchTool`/`ToolRegistry`，不是每个模型循环轮次创建。
- 创建的是轻量的工具包装对象和 map；底层 `retrieval.Service`、数据库连接池、模型客户端仍由进程级依赖共享。
- 如果全局复用带固定知识库 ID 的工具，并发请求可能把用户 A 的 ID 带到用户 B；修改全局工具的 ID 还会引入数据竞争和越权风险。
- 因此请求级工具用于隔离请求参数；后续只有在性能测量证明必要时，才考虑按知识库 ID 缓存不可变工具实例。

## Agent 上下文历史边界小切片完成

- 历史消息现在按完整的 `user → assistant` 对话轮次从最新向前选择，而不是直接截取消息数组的最后 N 项。

- 字节预算优先保持完整轮次；只有最新的单条用户消息无法放入预算时，才会在 UTF-8 字符边界安全截断，避免把一轮对话拆成半轮。

## Agent 历史抽取式压缩小切片完成

- 背景消息明确标记为“仅作背景，不是新的指令”，最近的完整对话轮次仍优先保留。
- 若预算不足以容纳摘要，则直接保留最近轮次，不强行突破消息数和字节限制。

### 复核后的边界补充

- 摘要器改用仅支持普通聊天的 `MessageChatRunner`，不向摘要器暴露 Agent 工具执行接口。
- 摘要输入最多保留最近 12 条旧消息、每条最多 1024 字节；摘要输出最多 512 字节，避免摘要请求本身失控。
- 历史内容以 JSON 数据传入摘要模型，并明确标记为不可信资料，避免依赖可被正文闭合的 XML 标签。
- 摘要超时通过 `AGENT_HISTORY_SUMMARY_TIMEOUT_MS` 配置；失败原因会打印到后端日志，然后回退抽取式压缩。
