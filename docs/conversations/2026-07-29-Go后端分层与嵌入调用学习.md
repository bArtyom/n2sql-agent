# Go 后端分层与嵌入调用学习

## 背景

围绕已完成的模型 Provider 连通性检测和嵌入调用功能，学习 Go 标准库 HTTP 后端如何从启动、路由、请求处理一路调用到数据库和外部模型服务。

## 已确认结论

### 后端分层职责

```text
main -> app -> handler -> service -> store/client
```

- `main`：读取运行配置，创建数据库连接和共享对象，将依赖组装后启动 HTTP Server。
- `app`：创建 `http.ServeMux`，将“HTTP 方法 + URL”注册到对应 Handler，是总路由接线层。
- `handler`：处理 HTTP 请求和响应，包括 JSON 解析、输入大小限制、输入校验、状态码与错误 JSON；不直接写 SQL 或调用模型 HTTP API。
- `service`：组合业务流程。例如嵌入服务读取 Provider 配置、读取环境变量 API Key、调用模型 Client。
- `store`：读写数据库。例如 `modelprovider.PostgresStore` 读取当前启用的模型配置。
- `client`：调用外部服务。例如 `modelclient.HTTPClient` 安全地请求模型 API。

### `ServeMux` 与 `http.Handler`

- `http.NewServeMux()` 是创建路由器的函数；它返回 `*http.ServeMux` 对象。
- Go 标准库中的 `ServeMux` 已经有 `ServeHTTP(http.ResponseWriter, *http.Request)` 方法，因此自动符合 `http.Handler` 接口。
- Go 接口是隐式实现：类型不需要显式写 `implements`，只要拥有接口要求的全部方法即可。
- `app.New(...)` 最后返回的 `mux` 是总 Handler；它内部保存“请求方法 + URL -> 具体 Handler”的对应关系。

### 嵌入请求完整链路

```text
POST /api/model-provider/embedding-test
  -> ServeMux 路由
  -> ModelProviderEmbeddingTest Handler
  -> EmbeddingService
      -> PostgresStore.Current() 读取 Provider
      -> os.LookupEnv() 读取 API Key
      -> HTTPClient.Embed()
  -> HTTPS POST {baseUrl}/embeddings
  -> 返回向量 JSON
```

### 嵌入 Handler

- 仅接受 `POST` 请求。
- 接收 `{"input":["文本1", "文本2"]}`。
- 限制请求总体大小、输入条数和单段文本大小，拒绝未知字段、尾随 JSON 和空文本。
- 调用 `runner.Embed(ctx, input)`，再根据错误类型转换为 `400/404/413/500/502`。

### EmbeddingService

- `EmbeddingService` 是业务组合层，不处理 HTTP JSON 或 SQL 细节。
- 它从 Store 获得 `BaseURL`、`EmbeddingModel` 和 `APIKeyEnvVar`。
- 它确认数据库记录中的密钥变量名符合本地服务配置，再通过 `os.LookupEnv` 取得真实密钥。
- 它把模型地址、模型名、密钥和文本交给 `HTTPClient.Embed`。

### HTTPClient

- 一个共享 `HTTPClient` 同时实现 `Check(...)` 和 `Embed(...)`；连接检测和嵌入调用复用同一套网络安全规则。
- Client 仅允许 HTTPS、`.env` 中允许的主机，并禁止自动跟随重定向。
- 嵌入调用使用 `POST {baseUrl}/embeddings`，设置 `Authorization: Bearer <API Key>` 和 `Content-Type: application/json`。
- 外部响应限制为 2MB，且必须包含与输入数量对应、索引合法且非空的向量。

### 分层取舍

- 不是每个小功能都要包含 Handler、Service、接口、Store、数据库和 Client。
- 例如“计算文本长度”只需 `main -> app -> Handler -> len(text)`。
- 嵌入功能涉及数据库配置、环境变量密钥、外部 HTTPS API 和安全边界，因此使用 Handler、Service、Store、Client 的分层是合理的。
