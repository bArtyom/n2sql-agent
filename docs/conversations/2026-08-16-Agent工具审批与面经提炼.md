# Agent 工具审批与面经提炼

## 用户提问记录

- 后端在确认审批功能中做了什么？实现了什么？
- 能否用最小实现的代码示例解释审批流程？
- 关键关注点：Agent 如何暂停、用户决定如何传回、工具如何保证在确认前不执行。

## 功能结论

Agent 在模型决定调用工具后，不能立即执行工具。后端先发送 `approval_required` 事件，然后通过一个阻塞的审批等待点暂停当前运行。前端展示工具名和参数摘要，用户选择允许或拒绝后，后端通过审批接口恢复运行。

核心链路：

```text
模型返回 ToolCall
    ↓
后端发送 approval_required
    ↓
Agent 阻塞等待 channel
    ↓
用户调用 approval 接口
    ↓
channel 返回 true/false
    ↓
允许：执行工具；拒绝：终止本次运行
```

## 面试表达

### 1. 为什么审批要放在后端？

因为前端只能展示和发起决定，不能成为安全边界。真正的工具调用发生在后端，所以必须在后端的 Tool Call 和 `tool.Call` 之间插入审批闸门，确保用户未确认时工具不会执行。

### 2. Agent 是怎么暂停的？

每个 Agent Run 在内存 Hub 中保存一个带缓冲的 `chan bool`。Agent 调用 `WaitApproval` 后阻塞在这个 channel 上；审批接口收到用户决定后调用 `ResolveApproval`，把布尔结果写回 channel，Agent 恢复执行。

### 3. 为什么使用 channel？

channel 很适合表达“一方等待，另一方稍后恢复”的一次性事件。它避免轮询数据库，也不需要让 HTTP 请求一直占用连接；审批接口和 Agent 执行协程只通过 Hub 解耦。

### 4. 如何避免误操作其他运行？

审批状态同时绑定 `knowledgeBaseID` 和 `runID`。接口解析路径参数后由 Hub 再次校验，其他知识库或不存在的运行无法提交审批。

### 5. 用户拒绝或运行取消怎么办？

拒绝返回 `false`，Engine 不执行工具并结束本轮运行；运行取消、结束或上下文超时会释放待审批状态，避免协程和 channel 泄漏。

### 6. 这个实现的限制是什么？

当前审批状态保存在进程内 Hub 中，服务重启或多实例部署时不能跨进程恢复。生产环境还需要 Redis/PostgreSQL 等共享状态、权限校验和更完整的工具参数编辑/审计记录。

当前标准流式 Agent 的审批等待默认有 30 秒超时。超时后 Engine 发送 `approval_expired`，不执行工具并结束本轮运行，避免 Agent 无限占用执行协程。
