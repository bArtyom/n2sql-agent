# 检索结果缓存

## 背景

同一知识库中，用户可能重复发送相同问题，或者多个请求同时询问同一个问题。每次都重新调用查询改写、Embedding、关键词检索和 Rerank，会增加延迟和模型成本。

## 本轮实现

- `retrieval.Service` 增加进程内检索结果缓存，缓存的是完整的“改写/召回/合并/Rerank”结果，不缓存最终 Chat 答案。
- 缓存键包含知识库 ID、规范化问题、limit、文档 ID 范围和 Query Rewrite 开关，避免不同检索条件错误复用结果。
- 缓存有 TTL 和最大条目数，使用最近使用顺序淘汰；默认 2 分钟、128 条，可通过 `RETRIEVAL_CACHE_TTL` 与 `RETRIEVAL_CACHE_ENTRIES` 调整。
- 同一缓存键的并发请求共享一次底层检索；失败不会写入缓存，调用方仍能看到真实错误。
- Worker 在文档重新索引成功后调用 `ClearCache(knowledgeBaseID)`，避免继续返回旧文本；服务重启也会清空进程内缓存。

## 调用链

```text
问题
  → retrieval.Service 规范化参数并生成缓存键
  → 命中：复制结果直接返回
  → 未命中：一个请求执行改写/向量/关键词/Rerank，其它相同请求等待
  → 成功结果写入缓存
  → RAG / Agent 继续调用 Chat 模型生成答案
```

## 注意事项

- 缓存只在当前 Go 进程有效，多实例部署时每个实例各自缓存；后续若需要跨实例一致性，再考虑 Redis。
- 修改模型、Rerank 配置后，已有结果最多保留到 TTL；如果要立即生效可重启服务或调用知识库失效入口。
- 当前验证覆盖缓存命中、查询规范化、结果复制、TTL、容量淘汰、失败不缓存和并发合并；没有调用真实模型或做多实例基准测试。
