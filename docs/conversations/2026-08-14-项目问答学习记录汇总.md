## 2. Go 后端整体架构

### 典型调用链

```text
用户/前端
  → main 组装依赖
  → app.New 注册路由
  → Handler 解析 HTTP
  → Service 编排业务
  → Store/Client 访问数据库或模型
  → 返回 JSON/SSE
```

### 各层职责

- `cmd/server/main.go`：程序入口、配置读取、数据库连接、实例创建和依赖注入。
- `internal/app/server.go`：把 URL 方法映射到 Handler，不承载具体业务。
- `internal/handler`：解析路径、JSON、状态码和 SSE；不直接写 SQL。
- `internal/*service`：业务流程、权限边界、超时、事务编排和接口组合。
- `internal/*store`：实现数据库读写接口。
- `internal/modelclient`：发起 OpenAI 兼容 HTTP 请求并解析响应。
- `internal/modelruntime`：把 provider 配置、API Key 和模型客户端组合成 Chat/Embedding 服务。

### 为什么要定义接口

例如：

```go
type DocumentReader interface {
    List(context.Context, int64) ([]Document, error)
}
```

Service 只依赖接口，不依赖具体 PostgreSQL 实现，因此可以：

- 用 stub 测试；
- 更换数据库实现；
- 让 Handler、Service、Store 职责清楚。

### `new` 的作用

Go 没有 Java Spring 的自动注入容器。`NewXxx` 通常是构造函数，负责创建带依赖的 struct；真正的注册仍由 `main` 和 `app.New` 完成。

`ServeMux` 实现 `http.Handler` 是因为它有：

```go
ServeHTTP(http.ResponseWriter, *http.Request)
```

`New` 只是返回对象；对象是否实现接口取决于它的方法集合，不是因为函数名字叫 `New`。

### `context.Context`

`ctx` 主要传递：

- 请求取消信号；
- 超时和截止时间；
- 少量请求范围元数据。

它不是业务数据容器，也不会自动执行后续函数。后续代码把同一个 `ctx` 传给数据库、HTTP 和模型调用后，这些调用才会响应取消和超时。

## 3. Docker、PostgreSQL 与迁移

### Docker 的作用

Docker Compose 当前只运行 PostgreSQL + pgvector，保证本机数据库版本和扩展一致。

```yaml
volumes:
  - ./.data/postgres:/var/lib/postgresql/data
  - ./db/init:/docker-entrypoint-initdb.d:ro
```

- `./.data/postgres`：把容器数据库目录映射到本机，容器删除后数据仍保留。
- `./db/init`：容器第一次初始化数据库时读取 SQL，只读挂载。
- 代码目录不需要整体挂进数据库容器；后端本机运行，代码仍在本机。

### 迁移

迁移程序按顺序执行 `internal/database/migrations/sql/*.up.sql`，记录已应用版本，避免重复执行。

例如：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

表示如果 PostgreSQL 中没有 pgvector 扩展就创建，有则不重复创建。

### 主要数据表

- `administrators`：管理员。
- `system_settings`：单管理员系统配置。
- `knowledge_bases`：知识库。
- `documents`：上传文档元数据。
- `document_processing_tasks`：文档处理任务和状态。
- `document_chunks`：切分后的父块/子块和 embedding。
- `conversations`：会话。
- `conversation_messages`：用户和助手消息，metadata 保存引用、统计和 Agent 轨迹。
- `a2a_tasks`：A2A 异步任务。

`conversation_messages` 只保存 `user/assistant` 两种持久化角色；模型内部的 `tool` 消息主要在一次 Agent Run 的内存上下文中流转，安全摘要和工具轨迹另存到 metadata。

## 4. 模型服务与环境变量

### API Key

- API Key 放在后端 `.env`，不会下发给前端。
- `.env` 中的变量需要成为 Go 进程的环境变量；Shell 中 `set -a; source .env; set +a` 会把变量导出给子进程。
- 程序当前没有默认自动解析 `.env` 文件，因此启动前需要导出变量，或使用已有启动脚本。

### 三层模型调用结构

```text
Agent/RAG Service
  → modelruntime.ChatService
  → modelclient.HTTPClient
  → OpenAI 兼容 /chat/completions HTTP 接口
```

- Go 默认 `http.Client` 只负责网络请求。
- 项目的 `modelclient.HTTPClient` 额外负责 URL 白名单、Authorization、JSON 编码、响应大小限制和 provider 响应解析。
- `ChatService` 负责读取当前 provider、API Key 和模型名称。

## 5. 文档处理与 RAG

### 文档处理流水线

```text
上传文件
  → 创建 document_processing_task
  → Worker 领取任务
  → extractor 读取 TXT/MD/PDF
  → 生成父块
  → 父块切成子块
  → 只对子块生成 embedding
  → 保存 document_chunks
  → 标记任务 succeeded/failed
```

### TXT、MD、PDF

- TXT：直接读取文本。
- MD：按文本读取，Markdown 标记暂时作为普通文本内容。
- 文本型 PDF：提取文本。
- 扫描 PDF：根据是否提取到有效文本决定是否进入 OCR 最小路线。

### 父块和子块

- 父块：提供较完整上下文。
- 子块：粒度更小，适合 embedding 和精确命中。
- 命中子块后加载对应父块，模型上下文使用父块，但引用保留子块位置。
- 同一个父块在上下文中只注入一次，避免重复占用 token。
- 旧数据没有父块时继续使用邻近 chunk 扩展。

### 向量检索

- embedding 保存到 PostgreSQL 的 `vector(1024)` 列。
- 小数据量时 PostgreSQL 可能顺序扫描。
- 数据增长后使用 HNSW cosine 索引，加速近似最近邻搜索。
- HNSW 类似多层导航图：先在稀疏高层快速定位，再逐层下降到更密集的底层。

### 关键词检索

- PostgreSQL 使用 `tsvector + GIN` 倒排索引，也保留 `pg_trgm` 模糊匹配能力。
- 关键词得分由 PostgreSQL 全文检索相关度计算，不要求每个词都命中。
- 多个词命中越多、位置越接近、词频和权重越高，通常得分越高。

### 混合检索与 Rerank

```text
向量召回 + 关键词召回
  → 去重
  → RRF/fusionScore 融合
  → 可选 Rerank
  → Rerank 失败回退到融合结果
  → 距离和关键词阈值过滤
  → 父块上下文扩展
```

检索统计包括：向量召回数、关键词召回数、阈值后数量、去重数、Rerank 前后数量和最终结果数。

## 6. Agent Runtime 与 Tool Calling

### Tool 接口

```go
type Tool interface {
    Name() string
    Description() string
    Parameters() json.RawMessage
    Call(context.Context, json.RawMessage) (ToolResult, error)
}
```

### ReAct 循环

```text
用户问题
  → 模型判断
  → 如果返回 tool_calls：执行工具
  → 工具结果放回消息
  → 再次调用模型
  → 没有 tool_calls 时视为最终回答
```

模型不会直接执行 Go 函数，只会返回结构化请求：

```json
{
  "tool_calls": [
    {
      "id": "call-1",
      "type": "function",
      "function": {
        "name": "document_list",
        "arguments": "{\\"limit\\":20}"
      }
    }
  ]
}
```

Go 通过 JSON 标签解析为：

```go
response.ToolCalls[0].Function.Name
response.ToolCalls[0].Function.Arguments
```

随后：

```go
tool, err := registry.Find(toolCall.Function.Name)
toolResult, err := tool.Call(ctx, []byte(toolCall.Function.Arguments))
```

`ToolRegistry` 使用名称到接口对象的 Map；Engine 不需要知道具体是搜索工具还是文档列表工具。

### 工具安全边界

- 校验工具 ID、类型、名称和参数 JSON。
- Registry allowlist 只允许当前注册的工具。
- `document_list` 不接受模型传入知识库 ID，服务端提前绑定当前知识库。
- 工具结果加上不可信结果封装，系统提示明确禁止执行工具结果中的指令。
- 工具结果限制长度，避免撑爆上下文。

### 当前标准 Agent 工具

- `knowledge_search`：根据问题查找相关文档片段。
- `document_list`：列出当前知识库的文件名、类型、大小和处理状态。
- `document_info`：根据文档 ID 查询单个文档的元数据和处理状态，不读取全文。

### `document_list` 完整链路

```text
main 注入 documentService
  → agentservice 创建当前知识库范围 Registry
  → 注册 knowledge_search/document_list/document_info
  → 模型选择 document_list
  → registry.Find("document_list")
  → DocumentListTool.Call
  → document.Reader.List
  → PostgreSQL documents 查询
  → 返回有界 JSON
  → 模型生成中文回答
```

## 7. SSE、事件、emitter 与 sink

### 事件为什么会自动触发

不是 `emit` 自己发现了事件，而是 Engine 在关键执行位置显式调用：

```go
emitter.emit(agent.EventToolCalled, ...)
emitter.emit(agent.EventToolFinished, ...)
emitter.emit(agent.EventMessageDelta, ...)
```

`emitter` 负责创建事件编号和统一格式，`sink` 是接收事件的函数。

```go
type EventSink func(agent.Event) error
```

事件链路：

```text
Engine
  → emitter.emit
  → sink(event)
  → traceCollector / citationCollector / SSE sink
  → Handler 写入浏览器
```

没有外部 sink 时，Agent 仍然能执行，只是不会把过程实时推到前端。

### SSE 的意义

普通 HTTP 是一次性返回最终结果；SSE 可以让前端看到：

```text
run_started
tool_called
tool_finished
message_delta
run_finished
```

## 8. 会话、引用和 Agent 轨迹

### 持久化内容

助手消息 metadata 中保存：

- 有界引用快照；
- 检索统计；
- 查询改写状态；
- 有界 Agent 工具轨迹。

工具轨迹保存：

- 工具名；
- 工具调用参数预览；
- 结果摘要；
- 状态和步骤。

不保存：

- 原始完整工具结果；
- 模型隐藏思考过程；
- 无界的大段上下文。

### 前端恢复

```text
历史消息 metadata
  → restoreAgentEvents
  → agentEvents
  → 轨迹卡片
```

当前工具轨迹默认折叠，用户点击箭头查看参数预览和结果摘要；展开状态只存在前端页面，不写数据库。

## 9. 可靠性与后端工程化问答

### Worker

- 定时轮询不是把所有逻辑放在 Handler，而是独立的后台生命周期。
- Worker 领取任务时用数据库状态和租约避免多个 Worker 同时处理。
- 失败任务按有限次数重试，指数退避，超过最大次数进入死信。
- 日志记录 task_id、document_id、状态、耗时和错误类别。

### 并发摘要锁

- 同一个会话可能同时收到多个请求。
- 进程内锁减少本机重复摘要。
- PostgreSQL advisory lock 解决多个进程/连接之间的会话级互斥。
- 锁覆盖读取历史、摘要、模型调用和保存结果的关键区间。

### 幂等

- 客户端通过 `Idempotency-Key` 标识同一次请求。
- 相同 key 和相同请求可以重放已有结果。
- 相同 key 但请求内容不同必须冲突。
- SSE 已发送 200 后无法再改成 HTTP 409，因此 SSE 冲突使用事件表达；跨实例原子 claim 仍是后续增强点。

### Request ID

- 合法的 `X-Request-ID` 可以复用；缺失或非法时由服务端生成。
- 放进 context：让下游日志自动关联同一次请求。
- 放进响应头：让客户端、浏览器和排障人员能看到并反馈这个 ID。

### Metrics

记录：

- Agent 运行次数、成功/失败、步骤数、工具调用数、token 和耗时；
- Worker 领取、成功、失败、取消、重试和死信；
- HTTP 请求数量、状态码和延迟。

## 10. Multi-Agent、MCP、A2A

### Multi-Agent

- `Researcher`：多轮检索、整理证据。
- `Answerer`：根据摘要和原始片段生成最终答案。
- `Supervisor`：编排两个角色，处理超时、取消、无证据拒答和最终输出。

Researcher 可以循环调用工具，但必须受到最大步骤、超时、重复查询和取消约束。

### MCP

- MCP Server 对外提供只读工具能力，例如 `knowledge_search` 和 `document_list`。
- MCP 不是 Agent 本身，而是工具/上下文接入协议。
- 当前实现是项目内的最小 HTTP JSON-RPC 适配，不宣称完整官方 MCP 互操作。

### A2A

- A2A 是 Agent 与 Agent 之间的任务通信。
- 当前实现包括 Agent Card、任务创建、状态查询、结果返回和 PostgreSQL 持久化。
- A2A 任务由后台 Runner 异步执行并复用 Multi-Agent Supervisor。

## 17. 2026-08-23：MIME 与图片文件类型

- MIME 类型用于描述数据格式，基本形式是 `主类型/子类型`，例如 `text/plain`、`application/pdf`、`image/png`。
- 文件扩展名、MIME 类型和文件头不是同一个概念：扩展名容易被修改，客户端 MIME 也可能伪造，文件头的 Magic Bytes 可用于验证真实格式。上传安全应综合检查扩展名、MIME、文件头和实际解析结果。
- 常见图片类型：PNG 无损且支持透明，适合截图、文字和图表；JPEG 有损压缩且体积小，适合照片和扫描件；WebP 同时支持有损、无损、透明和动画，体积通常更小；GIF 适合简单动画；SVG 是 XML 矢量格式，需要额外做脚本和外部资源清洗。
- 常见文档本质：TXT/Markdown 是文本，HTML 是带标签的文本，PDF 是页面描述格式，DOCX/XLSX/PPTX 是 ZIP + XML，PNG/JPEG/WEBP 是二进制图片。
- HTTP 上传通常使用 `multipart/form-data`，文件部分携带 `Content-Disposition` 和 `Content-Type`；下载时服务器通过 `Content-Type` 和 `Content-Disposition` 控制浏览器展示或下载。
- Base64 不是文件格式，而是把二进制转换成文本的编码方式。Vision 请求中的 `data:image/png;base64,...` 由 Data URL、MIME 类型和 Base64 数据组成。
- 在本项目中，MIME 类型决定解析路由：文本直接读取，Office 文件解析 XML，PDF 提取文字或 OCR，图片交给 Vision/OCR，再统一进入切分、Embedding 和关键词检索。
- 文件上传必须设置白名单、大小限制、路径安全、ZIP 解压限制、超时和并发限制；SVG 等同时具备文档/脚本能力的类型需要额外清洗，未实现清洗前不应随意放开。

## 18. 2026-08-27：面经第 3 题——ReAct Agent 完整调用链

### 面试问题

请介绍项目中的 ReAct Agent 是如何实现的？Agent 在什么情况下容易陷入思考死循环（Thought Loop）？

### 标准回答

ReAct 的核心是让模型交替完成“思考、行动、观察”几个阶段。用户问题进入后，后端把固定系统提示词、历史消息和独立的工具定义发送给模型。模型如果返回 `tool_calls`，Agent Engine 就根据工具名从 Tool Registry 查找工具，校验参数后执行，并把工具结果以 `tool` 消息追加回当前上下文，再调用模型判断下一步。模型没有返回工具调用时，才把本次输出视为最终答案。整个循环受到最大模型轮次、上下文预算、取消信号和工具错误处理约束。

思考死循环通常来自：没有最大步数或总 Token 预算；模型反复调用同一个工具；工具结果始终为空或不能解决问题；工具错误没有反馈给模型进行修正；工具参数校验和重试边界不清晰；检索结果相互矛盾导致模型不断扩大搜索范围。工程上可以记录工具调用签名，检测连续重复调用；限制单工具重试次数和 Agent 最大步数；对工具错误返回结构化、可修正的错误信息；达到边界后安全结束并说明原因，而不是无限调用。

### 一轮完整消息链

以“查员工手册中的年假规则”为例：

```text
用户问题
  → 模型请求：system + history + tools
  → assistant：tool_call(knowledge_search)
  → 后端执行知识库检索
  → tool：返回检索结果和引用
  → 模型请求：追加 assistant tool_call + tool result，并再次发送 tools
  → assistant：直接生成最终答案，或继续调用 document_read
  → message_delta：答案增量通过 SSE 返回
  → run_finished：保存最终答案、引用、状态和统计
```

工具定义不进入消息历史，而是放在模型 API 的 `tools` 字段中。由于模型 API 通常是无状态的，每次模型调用都要重新携带当前可用工具定义；但后端不需要每轮重新计算工具列表，只有权限、知识库模式或 Agent 阶段变化时才重新过滤。这样既符合 Function Calling 协议，也能保持工具 Schema 稳定，有利于前缀 Prompt Cache。

### DeerFlow 风格的记忆与流式展示

DeerFlow 使用 Middleware 在第一次运行时注入隐藏的记忆上下文，记忆作为独立消息存在，不直接拼接到用户问题后面；注入后的会话状态会被 checkpoint 保存，后续轮次直接复用。工具调用过程通过运行事件展示给前端，例如 `run_started`、`tool_called`、`tool_finished`、`message_delta` 和 `run_finished`；模型内部完整思维链不作为普通消息长期保存。

本项目对应代码：`internal/agentruntime` 负责 ReAct 循环和工具调用，`internal/agent` 负责工具定义与实现，`internal/agentstream` 和 `internal/handler` 负责事件与 SSE，`internal/conversation` 负责保存用户消息、助手答案和可恢复元数据。

## 19. 2026-08-27：面经第 4 题——运维 API 超时与 5xx 容错

### 用户回答复盘

回答抓住了两个核心方向：对临时故障设置有限次数的重试，超过阈值后使用降级方案；Agent 运行层通过 Worker 领取任务、记录步骤和 checkpoint，在 Worker 失败后由其他 Worker 接管并从断点恢复。需要补充的是，不能把所有错误都统一重试三次，也不能把“运维 API 降级”简单等同为“切换模型 API”。还要说明退避、熔断、幂等和超时后的不确定状态处理。

### 标准回答

我会先对错误分类，再决定是否重试。网络超时、连接暂时失败、429、502、503、504 等通常属于临时错误，可以在请求截止时间内做有限次数重试；参数非法、认证失败、权限不足等 4xx 通常不可重试，应直接反馈明确错误。重试不能固定立即连续发送，而应使用指数退避加随机抖动，例如第 1 次等待 200ms、第 2 次等待 400ms、第 3 次等待 800ms，并设置总超时和最大重试次数，避免放大上游压力。

如果连续失败达到阈值，就打开熔断器，短时间内快速失败，避免每个 Agent 都继续请求已经不可用的上游；经过冷却时间后进入半开状态，允许少量请求探测恢复。降级目标应与故障对象匹配：运维 API 故障时切换备用运维 API 或返回可解释的不可用状态；模型 API 故障时才切换备用模型或 Provider。降级过程需要记录错误分类、尝试次数、耗时和最终使用的 Provider。

对于有副作用的运维操作，超时不代表操作一定没有发生，不能直接盲目重试。应使用幂等键、查询外部操作状态或人工审批确认；只读工具通常可以安全重试，副作用工具默认需要审批，只有证明幂等后才允许自动重试。

Agent 执行层还要与 API 容错分开：`agent_runs` 持久化运行状态、尝试次数、租约和错误分类；Worker 通过心跳续租，崩溃后由过期租约回收逻辑把任务重新置为 `pending`，新的 Worker 再用 `FOR UPDATE SKIP LOCKED` 领取。checkpoint 保存已经完成的步骤和可复用结果，普通只读工具可以复用，避免重复调用；副作用工具必须继续遵守审批和幂等边界。最终状态和答案写入 PostgreSQL，运行事件通过 SSE/Redis 发送给前端。

### 面试评分要点

- 已覆盖：有限重试、降级、Worker 接管、checkpoint 断点恢复。
- 需要补充：错误分类、指数退避与随机抖动、熔断、请求总截止时间、幂等键和超时不确定状态。
- 表述修正：运维 API 的降级优先切换备用业务 API；只有模型服务故障时才切换备用模型。
