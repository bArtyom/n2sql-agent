# Agent SSE 断线恢复

## 背景

标准 Agent 已经通过 SSE 推送运行轨迹，但浏览器、代理或网络短暂断开时，原请求的 HTTP 流会消失。若只依赖原连接，用户只能重新发起一次模型请求，既看不到已经生成的内容，也可能重复消耗模型调用。

## 本轮结论

- 后端为每次标准 Agent 流创建一个随机 `run_id`，通过 `X-Agent-Run-ID` 响应头和事件体返回。
- 新增进程内 `agentstream.Hub`，按知识库隔离保存最近 128 个运行，每个运行最多保留 512 个事件，默认保留 10 分钟。
- Agent Engine 事件和会话保存/重放/失败事件都进入 Hub；原 SSE 连接仍实时接收，重连端先读取历史再接收后续事件。
- 新增 `GET /api/knowledge-bases/{id}/agent-runs/{runID}/stream`，只允许同一知识库范围读取运行事件。
- 前端保存 `run_id`，按事件 `id` 去重；原流读取失败或提前结束时，自动请求恢复路由，不会重新调用模型。
- Agent 执行使用脱离请求取消的上下文继续完成，避免浏览器断开导致模型运行和会话保存被中途取消。

## 调用链

```text
浏览器 POST agent-chat/stream
  → Handler 生成 run_id、Hub.Start
  → AgentService/Engine 产生事件
  → Handler 同时写原 SSE 和 Hub
  → 浏览器断线
  → GET agent-runs/{runID}/stream
  → Hub snapshot（历史）+ live channel（后续）
  → 前端按 event id 去重并恢复答案/引用/状态
  → Handler 完成后 Hub.Finish，订阅端收到关闭信号
```

## 重要边界

- Hub 是进程内短期缓存，不是 PostgreSQL/Redis 持久队列；服务重启或运行超过 TTL 后不能恢复。
- 多实例部署时每个实例的 Hub 不共享，后续若需要生产级恢复应把事件放到 Redis、消息队列或持久化表，并增加实例路由/共享存储。
- 断线恢复只重放同一次 Agent Run，不提供“成功回答编辑后覆盖历史”的能力，也不会因为重连再次调用模型。
- Hub 有运行数、单运行事件数、TTL 和有界 live channel 上限，避免无限占用内存；慢订阅者可依靠保留的事件历史重新连接。
- 当前路由沿用项目现有知识库访问边界；随机 `run_id` 不是权限凭证，不能替代后续认证与多租户授权。
