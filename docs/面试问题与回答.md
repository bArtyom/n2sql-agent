## 文档切分的三层策略怎么设计？

### 推荐回答

在文档切分方面，我采用了“结构化优先、启发式识别、递归兜底”的三层策略。

第一层是结构化标题切分。对于 Markdown 等包含明确层级标题的文档，我会解析 `#` 到 `######` 的标题层级，维护一个标题栈，为每个 Chunk 保存完整的 `heading_path`，例如“部署指南 > Docker > Windows”。这样既能保留文档上下文，也方便后续关键词检索、向量检索和引用展示。

第二层是启发式标题切分。对于 TXT、PDF 或 DOCX 转换后没有标准 Markdown 标记的文档，我会根据“第一章”“1.1”“Chapter 1”等章节格式、全大写标题和页面分隔符识别潜在标题，并生成语义路径。

第三层是递归切分兜底。如果文档没有任何可识别结构，就使用递归字符切分，根据段落、换行、句号等分隔符，并通过重叠窗口减少上下文断裂。此时会生成“文件名 > 第 N 段”这样的虚拟路径，但虚拟路径只用于定位和引用，不会加入 Embedding，避免污染语义。

整个流程不是固定只使用一种策略，而是优先尝试结构化切分，并对 Chunk 数量、长度和过碎情况进行质量检查。如果当前策略结果不理想，就自动降级到下一种策略。这样既能尽量保留原文结构，又能保证没有标题的普通文档也可以被稳定索引。

### 关键词

- 结构化切分
- 启发式标题识别
- 递归切分
- `heading_path`
- 虚拟路径
- Chunk 质量检查
- 降级策略
- Embedding 输入与原文存储分离

## ReAct Agent 是如何实现的？

### 面试题

假设用户提问：

> 请总结知识库中的《Go面经记录.md》。

请说明：

1. Agent 如何决定调用哪个工具？
2. 一次 Thought → Action → Observation 循环是什么？
3. 知识库检索结果如何回到 Agent 上下文？
4. Agent 在什么条件下结束？
5. 如何防止 Agent 陷入 Thought Loop？
6. `AgentMaxSteps` 由模型负责还是后端负责？

### 核心结论

本项目的 Agent 外层采用类似 ReAct 的工具调用循环，但模型不直接执行工具：

```text
用户问题
  ↓
模型读取工具描述和参数 Schema
  ↓
模型返回结构化 tool_calls
  ↓
后端校验工具、参数、权限和审批要求
  ↓
后端执行工具
  ↓
工具结果以 tool message 加入上下文
  ↓
模型继续决策或生成最终答案
```

模型返回的不是普通文本，而是类似下面的结构化调用：

```json
{
  "tool_calls": [
    {
      "id": "call_1",
      "function": {
        "name": "document_summary",
        "arguments": {"document_id": 1}
      }
    }
  ]
}
```

后端还要检查工具是否存在、参数是否符合 Schema、文档是否属于当前知识库、用户是否有权限，以及工具是否需要审批。模型只能提出调用建议，不能直接获得执行权。

### 一次 Thought → Action → Observation

以“总结《Go面经记录.md》”为例：

1. **Thought**：模型判断用户要总结完整文档，因此优先选择 `document_summary`，不一定先调用 `knowledge_search`。
2. **Action**：模型返回 `document_summary({"document_id": 1})`。
3. **后端执行**：后端校验文档权限，执行摘要工具，限制结果大小并整理引用。
4. **Observation**：工具结果作为 `tool message` 放回上下文，例如：

```json
{
  "document_id": 1,
  "summary": "本文主要介绍 Go 面试中的并发、调度、内存管理和工程实践……",
  "source": "1:summary"
}
```

5. **下一轮模型调用**：模型根据摘要生成回答；如果没有新的 `tool_calls`，本轮结束。

工具结果不是把数据库内容不加处理地全部放回模型，而是经过截断、脱敏、引用提取和必要的结果压缩。知识库内容只能作为事实资料，不能被当作系统指令执行，以防止文档 Prompt Injection。

### `knowledge_search` 工具内部的 RAG 流程

Agent 外层只负责决定调用 `knowledge_search`；向量、关键词和图谱检索属于工具内部：

```text
knowledge_search
  ↓
可选查询改写
  ↓
PostgreSQL + pgvector 向量召回
  ↓
PostgreSQL tsvector/GIN 全文关键词召回
  ↓
可选 GraphRAG 侧路召回
  ↓
去重与 RRF 融合
  ↓
可选 Reranker 重排
  ↓
返回有限 Chunk、来源 ID 和引用信息
```

需要注意：

- 查询改写是可选的，失败时回退到原始问题。
- 关键词检索不是简单手动拆词，而是 PostgreSQL 全文检索和辅助评分。
- GraphRAG 不是每次都执行，只有开启后才作为额外召回侧路。
- 最终结果数量由 `topK` 决定，不能绝对地说固定返回 Top5。

典型检索结果如下：

```json
{
  "sources": [
    {
      "source_key": "1:8",
      "document_id": 1,
      "position": 8,
      "content": "Go 的 GMP 模型由 G、M、P 三部分组成……",
      "heading_path": "并发模型 > GMP"
    }
  ]
}
```

### Agent 的结束条件

不能简单说“模型输出 `finished` 状态后结束”。更准确的判断是：

```go
if len(response.ToolCalls) == 0 && strings.TrimSpace(response.Message) != "" {
    // 没有新的工具调用，并且回答非空
    // 认为 Agent 已经生成最终答案
}
```

也就是模型返回普通的 assistant 内容，并且没有新的 `tool_calls` 时，后端结束本轮 Agent。

其他强制结束情况包括：

- 达到最大步骤数；
- 上下文被取消；
- 工具超时；
- 不可重试的副作用工具失败；
- 持续重复调用相同工具；
- 模型返回空答案；
- Worker 任务被取消。

### 如何防止 Thought Loop

项目采用多层后端限制：

1. **最大步骤数**：`step >= maxSteps` 时停止 Agent。
2. **重复工具调用检测**：根据“工具名 + 规范化参数”生成调用 Key，连续重复时先反馈模型，持续重复则停止。
3. **工具结果大小限制**：过大的工具结果截断或保存到外部结果文件，只把必要内容放入上下文。
4. **历史上下文压缩**：旧消息和旧工具结果总结成短记忆，避免上下文无限增长。
5. **工具失败反馈**：普通只读工具失败时，把错误作为工具消息交给模型重新判断；副作用工具不能无条件自动重试，需要审批或幂等保证。

### Token 限制和步骤限制的区别

`max_completion_tokens` 只限制一次模型 API 调用最多生成多少 Token，例如一次工具决策或一次最终回答。

`maxSteps` 限制整个 Agent 最多循环多少轮：

```text
模型决策 → 工具执行 → 再次模型决策
```

如果需要限制整个任务的 Token 成本，还需要后端累计每次调用的：

```text
prompt_tokens + completion_tokens + embedding_tokens
```

超过总预算后，后端停止下一次模型调用。因此最终控制关系是：

> `max_completion_tokens` 控制单次模型输出长度，`maxSteps` 控制 Agent 循环次数，总 Token 预算和安全终止条件由后端强制控制，不能完全交给模型。

### 面试版完整回答

我的 Agent 外层采用类似 ReAct 的工具调用循环，但模型并不直接执行工具。后端会把当前消息、历史上下文和工具的 Function Calling Schema 一起发送给模型，模型返回包含工具名和 JSON 参数的结构化 `tool_calls`。后端收到后会校验工具是否存在、参数是否合法、用户是否有权限，以及工具是否需要审批，然后执行工具，并把工具结果以 `tool message` 的形式追加回上下文，再次调用模型。

以知识库问答为例，模型可能决定调用 `knowledge_search`。该工具内部由检索服务完成可选查询改写、PostgreSQL + pgvector 向量召回、PostgreSQL 全文关键词召回和可选 GraphRAG 召回，然后对结果进行去重和 RRF 融合；如果配置了 Reranker，再进行重排，最后返回有限的 Chunk、来源 ID 和引用信息给 Agent。

当模型返回普通 assistant 内容且没有新的 `tool_calls` 时，后端判定它已经生成最终答案并结束本轮，而不是依赖模型输出一个 `finished` 字段。后端还通过最大步骤数、重复工具调用检测、工具结果大小限制、上下文压缩、取消信号和错误重试策略防止 Thought Loop。

`maxSteps` 由后端控制 Agent 最多循环多少轮，`max_completion_tokens` 只限制单次模型调用的输出长度。如果还要限制整个 Agent 的 Token 成本，则由后端累计模型和 Embedding 的 Token 用量，超过总预算后停止继续调用。模型只负责提出决策，最终的限制和终止由后端负责。

#### 第 4 题追问：指数退避与随机抖动

指数退避是失败后逐步拉长下一次重试等待时间。常见公式是：

```text
delay = min(maxDelay, baseDelay × 2^attempt)
```

例如基础等待 100ms，最大等待 2s：

```text
第 1 次失败后：100ms
第 2 次失败后：200ms
第 3 次失败后：400ms
第 4 次失败后：800ms
```

随机抖动是在这个等待时间附近增加随机性。常用的 Full Jitter 是：

```text
delay = random(0, calculatedDelay)
```

例如计算出的等待时间是 400ms，不同 Worker 可能分别在 73ms、218ms、391ms 后重试，而不是全部在 400ms 同时重试。

如果 100 个 Worker 因同一个 5xx 同时失败：

```text
固定等待：100 个 Worker 同时再次请求
指数退避：请求逐渐拉开时间
指数退避 + 随机抖动：请求进一步打散
```

这样可以避免服务恢复瞬间被重试流量再次压垮，也就是避免 Thundering Herd（惊群）问题。429 限流响应如果带有 `Retry-After`，应优先遵守服务端给出的等待时间；最终等待时间还应该设置上限。

重试只应发生在可重试错误上，例如超时、连接异常、429、临时依赖故障和部分 5xx。400 参数错误、401/403 权限错误和用户取消不应该重试。

当前项目的模型调用重试总共最多 3 次，但等待时间仍是固定短延迟；指数退避和随机抖动属于下一步可优化项。当前项目的普通工具失败主要是把错误反馈给模型，由模型决定是否再次调用；有副作用的工具必须结合审批、幂等键或外部状态查询后才能重试。

面试中可以这样回答：

> 指数退避是每次失败后按照 2 的指数级逐渐增加等待时间，随机抖动是在等待区间内加入随机值，从而避免多个 Worker 同时重试造成惊群。实际实现会先判断错误是否可重试，对超时、429 和临时 5xx 使用带上限的指数退避；对参数错误、权限错误和取消请求不重试。对于有副作用的操作，还要先通过幂等键或状态查询确认是否已经执行，不能仅因为请求超时就直接重试。

### 第 3 题练习记录：ReAct 与 Thought Loop（2026-08-25）

#### 本次回答要点

用户回答已经覆盖了 ReAct 的主线：

```text
模型思考 → 调用工具 → Observation → 模型继续思考
```

并且提到了最大轮数、单次 Token、总 Token、重复调用和工具重试次数等限制。

#### 需要修正的地方

- 面试中建议说“模型返回工具调用决策”，不要把 Thought 表述成一定会暴露给前端的完整思维过程。
- `max_completion_tokens` 只能限制一次模型输出长度，不能单独防止逻辑死循环。
- 总 Token 预算可以控制成本和总执行量，但防止循环的第一道防线仍然是后端 `maxSteps`。
- “工具调用重试次数”主要解决临时错误；“重复调用检测”才是针对模型反复调用同一个工具的专门机制。
- 还应补充工具参数校验、权限检查、工具结果大小限制、历史上下文压缩和取消信号。

#### 标准答案

我的 Agent 外层采用类似 ReAct 的工具调用循环。用户提交问题后，后端会把用户消息、历史上下文以及可用工具的 Function Calling Schema 一起发送给模型。模型根据工具描述和参数约束返回结构化的 `tool_calls`，其中包含工具名称和 JSON 参数。

后端不会直接信任模型的调用结果，而是先校验工具是否存在、参数是否合法、用户是否有权限，以及该工具是否需要审批。校验通过后，后端执行工具，并把工具结果封装成 `tool message` 追加回上下文，再次调用模型。模型读取工具结果后，可以继续调用其他工具，也可以直接生成最终回答，这就形成了“模型决策 → 工具执行 → 结果观察 → 再次决策”的 ReAct 循环。

例如用户要求总结一份知识库文档，模型可能调用 `document_summary`；如果用户提出需要查找相关资料，模型可能调用 `knowledge_search`。`knowledge_search` 工具内部再执行向量召回、关键词召回、可选 GraphRAG、RRF 融合和 Rerank，但这些属于工具内部的 RAG 流程，不应和 Agent 外层循环混为一谈。

当模型返回非空的 assistant 内容，并且没有新的 `tool_calls` 时，后端认为模型已经生成最终答案，结束本轮 Agent。后端不依赖模型返回一个绝对可靠的 `finished` 字段。

为了防止 Thought Loop，后端会设置最大步骤数 `maxSteps`，检测相同工具和相同参数的重复调用，限制工具结果大小，压缩历史上下文，并设置总 Token 预算。普通只读工具失败时，可以把错误作为工具消息反馈给模型，让模型修改参数或选择其他工具；有副作用的工具则需要审批和幂等控制，不能无限自动重试。

其中，`max_completion_tokens` 限制单次模型调用的输出长度，`maxSteps` 限制 Agent 循环次数，总 Token 预算限制整个任务的资源消耗。这些安全限制最终都由后端强制执行，不能完全交给模型。

#### 相关疑问：工具列表和工具 Schema 是否每轮都发送？

是的。正常每次调用聊天模型时，工具定义都会通过请求的 `tools` 字段再次发送；它不是作为一条 `system` 或 `user` 消息拼接进 `messages`。当前 Engine 在一次 Run 开始时生成一次稳定的 `FunctionDefinitions`，之后每轮复用这份定义；ChatService 在每次模型请求中把它转换为 OpenAI 兼容的工具格式。

因此要区分两个概念：

```text
工具定义：每次模型 API 请求通过 tools 字段发送
工具执行过程：每轮把 assistant tool_calls 和 tool 结果追加到 messages
```

以两轮调用为例：

```json
{
  "model": "chat-model",
  "messages": [
    {"role": "system", "content": "系统规则、知识库策略、用户记忆"},
    {"role": "user", "content": "请总结 Go 面经文档"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "document_summary",
        "description": "总结指定文档",
        "parameters": {"type": "object", "properties": {"document_id": {"type": "integer"}}}
      }
    }
  ]
}
```

模型返回工具调用后，后端执行工具，并把两条消息加入下一轮上下文：

```text
assistant: tool_calls = document_summary({"document_id": 1})
tool:     {"document_id": 1, "summary": "……", "source": "1:summary"}
```

第二次请求大致变成：

```json
{
  "messages": [
    {"role": "system", "content": "系统规则、知识库策略、用户记忆"},
    {"role": "user", "content": "请总结 Go 面经文档"},
    {"role": "assistant", "tool_calls": ["document_summary(...)" ]},
    {"role": "tool", "tool_call_id": "call_1", "content": "摘要和引用"}
  ],
  "tools": ["同一组工具定义"]
}
```

如果工具结果或历史过大，下一轮发送前会进行上下文压缩：优先保留当前问题和最近工具结果，较早内容压缩成短记忆。工具定义本身仍然保持完整，因为模型需要知道当前允许调用哪些工具。

当前项目一次 Agent 请求的提示结构可以概括为：

```text
ChatRequest
├── model
├── messages
│   ├── system：Agent 规则、知识库模式、引用规则、用户记忆
│   ├── system：历史摘要（如果历史被压缩）
│   ├── user/assistant：保留的会话历史
│   ├── user：当前问题和附件
│   ├── assistant：上一轮的 tool_calls
│   └── tool：后端执行后的工具结果
├── tools：工具名、描述、JSON 参数 Schema
├── reasoning_effort：思考强度（可选）
└── max_completion_tokens：本次输出上限（可选）
```

所以，工具列表不是“只在第一轮追加一次”。正常每一次模型 API 请求都带上 `tools`，但工具列表通常不会随着循环变化。它的代价是工具定义会重复占用输入上下文；部分模型供应商可能提供 Prompt Cache 来降低重复前缀成本，但后端不能假设一定存在缓存。当前项目通过 `usage` 记录每次模型调用的 Token 用量。

特殊情况是断点恢复：如果 Worker 读取了已经持久化的模型决策和工具 checkpoint，可以直接复用这次决策，不再重复调用模型；此时当然也不会产生新的模型请求。

#### 追问：每轮都发工具定义，会不会造成重复和上下文过大？

会重复发送，但要区分“请求重复”和“会话历史重复”：

- 工具定义不会被追加成多条 `system/user/tool` 历史消息；
- 它作为当前模型请求的 `tools` 字段独立发送；
- 因为大多数模型 API 是无状态接口，所以每次请求都需要重新告诉模型当前允许使用哪些工具。

因此，第二轮请求不是在历史里再增加一份工具说明，而是请求体再次携带同一份 `tools` 配置：

```text
第 1 次请求：messages + tools
第 2 次请求：messages（增加 tool_calls/tool result）+ 同一份 tools
第 3 次请求：messages（继续增加结果）+ 同一份 tools
```

它确实会产生额外的输入 Token 成本，尤其是工具很多、每个工具描述和参数 Schema 很长时。当前项目的工具数量相对有限，所以优先保证模型每轮都能看到完整、稳定的能力边界。

常见优化方式有：

1. **按请求建立工具子集**：知识库问答只暴露 `knowledge_search`、`document_read`、`document_summary` 等相关工具，不把无关工具全部发送。
2. **缩短描述和 Schema**：描述只保留用途、必要参数和限制，不把完整业务文档放进工具描述。
3. **使用 Prompt Cache**：如果模型供应商支持，可以缓存稳定的 system prompt 和 tools 前缀，减少重复计算或计费；但这属于供应商能力，后端仍按每次请求完整发送。
4. **工具分层或延迟发现**：第一轮只提供少量工具或工具目录，模型需要时再加载更具体的工具；这会降低 Token，但增加一次发现流程和模型决策复杂度。
5. **保持工具集合稳定**：同一个 Agent Run 内不要无故修改工具列表，便于供应商做前缀缓存，也让模型的能力边界保持一致。

当前项目已经做了第一层的基础：根据请求模式创建受限的 `ToolRegistry`，子 Agent 也使用独立的工具白名单；但还没有实现供应商级 Prompt Cache 或动态工具发现。面试时可以这样回答：

> 工具定义会随每次无状态模型请求重新发送，但不会重复写入会话历史。这样做是为了保证模型每轮都知道当前可用工具。工具很多时会增加输入 Token，因此工程上通过请求级工具白名单、精简 Schema、Prompt Cache 和必要时的延迟工具发现来控制上下文成本。

#### 追问：为什么不把工具定义直接放进 System Prompt？

因为 System Prompt 和 `tools` 字段承担的职责不同：

```text
System Prompt：告诉模型应该如何行为
tools 字段：告诉模型当前有哪些可调用能力，以及参数 Schema
```

System Prompt 适合放规则，例如：

```text
需要事实资料时调用知识库工具；资料不足时不要编造答案。
```

`tools` 字段则使用模型 API 能识别的结构化协议：

```json
{
  "type": "function",
  "function": {
    "name": "knowledge_search",
    "description": "检索当前知识库",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {"type": "string"}
      },
      "required": ["query"]
    }
  }
}
```

如果把完整工具定义只放到 System Prompt 中，模型看到的只是普通文本或 JSON，模型服务不会把它当成原生 Function Calling 能力。这样会产生几个问题：

- 模型可能只输出一段看起来像工具调用的文本，而不是结构化 `tool_calls`；
- 后端需要自己从文本中解析工具名和参数，稳定性更差；
- 参数 Schema 不会被模型 API 和 SDK 按工具协议处理；
- 无法自然使用供应商提供的工具选择、并行工具调用和工具调用 ID；
- System Prompt 中的文字不能替代后端真正的工具白名单和权限校验。

所以两者通常配合使用：

```text
System Prompt：什么时候应该调用、只能依据什么回答、哪些行为被禁止
tools 字段：可以调用哪些工具、工具描述是什么、参数格式是什么
后端注册表：最终允许执行哪些工具、权限和审批如何校验
```

面试时可以这样回答：

> 工具定义不直接放进 System Prompt，是因为 System Prompt 是自然语言行为规则，而工具定义属于模型 API 的结构化能力协议。放在 `tools` 字段后，模型服务才能按 Function Calling 解析工具、校验参数并返回结构化 `tool_calls`。System Prompt 仍然需要保留，用来约束什么时候调用工具、如何使用工具结果；而真正的权限和安全边界由后端工具注册表负责。

#### 追问：模型会特殊处理 `tools` 这一批内容吗？

会。`tools` 不是普通的提示词字符串，而是聊天模型 API 约定的结构化请求字段。后端发送 JSON 请求后，模型服务通常会经过下面的转换：

```text
后端 ChatRequest.tools
  ↓
模型服务解析工具名称、描述和 JSON Schema
  ↓
按照具体模型的 Chat Template/工具调用格式组织输入
  ↓
模型判断是否调用工具
  ↓
返回结构化 tool_calls
```

例如后端发送：

```json
{
  "messages": [
    {"role": "user", "content": "查一下 Go 的 GMP 模型"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "knowledge_search",
        "description": "检索当前知识库",
        "parameters": {
          "type": "object",
          "properties": {
            "query": {"type": "string"}
          },
          "required": ["query"]
        }
      }
    }
  ]
}
```

模型服务会把这份工具定义以该模型训练时认识的特殊格式放入模型输入上下文。不同模型可能使用不同的内部模板，但对本项目的 HTTP 客户端来说，统一使用 OpenAI 兼容的 `tools` 协议即可。

模型最终不会直接执行 `knowledge_search`，而是返回类似：

```json
{
  "tool_calls": [
    {
      "id": "call_1",
      "type": "function",
      "function": {
        "name": "knowledge_search",
        "arguments": "{\"query\":\"Go GMP 模型\"}"
      }
    }
  ]
}
```

后端收到 `tool_calls` 后，才真正查找注册表、校验参数、执行工具，并把结果作为 `tool` 消息送回下一轮模型。

需要注意兼容边界：不是所有模型或供应商都支持原生 Function Calling。当前项目的 `ChatService` 使用 OpenAI 兼容的 `tools` 请求协议，因此选择模型时必须确认供应商或本地推理服务支持工具调用；如果不支持，就只能退化成“把工具说明写进 Prompt，再解析模型文本”的方案，可靠性和参数约束都会更差。

一句话总结：

> `tools` 的内容最终也会进入模型的输入上下文，但它不是普通文本，而是由模型服务按照工具调用协议特殊编码；模型据此输出结构化 `tool_calls`，真正执行仍由后端完成。

#### 第 5 题学习记录：Redis 数据结构与 Agent 缓存

本次回答：知道 Agent 可以使用 Redis，但暂时不了解 Redis 数据结构和选型。

Redis 是一个以内存为主的 Key-Value 数据库。常见数据结构如下：

| 类型 | 结构特点 | Agent 中的常见用途 |
| --- | --- | --- |
| String | 一个 Key 对应一个字符串或二进制值 | JSON 上下文快照、缓存结果、计数器 |
| List | 有序元素列表 | 按顺序追加消息、保留最近 N 条消息 |
| Hash | 一个 Key 下有多个字段 | Run 状态、租约、尝试次数等结构化状态 |
| Set | 无序且元素唯一 | 已处理工具 ID、权限集合、去重集合 |
| Sorted Set | 元素带分数，可按分数排序 | 优先级队列、延迟任务、按时间排序 |
| Stream | 带递增消息 ID 的追加日志 | Agent 流式事件、消费组、断线后按游标读取 |

当前项目中要区分三种数据，不应该全部塞进同一个 Redis Key：

```text
agent:context:{run_id}  → String 或 List，短期对话上下文缓存
agent:state:{run_id}    → Hash，运行状态和租约信息
agent:events:{run_id}   → Stream，临时 Agent 事件流
```

如果缓存的是“已经组装好的完整上下文快照”，推荐使用 String 保存 JSON：

```text
SET agent:context:21 '{"messages":[...]}' EX 3600
```

如果希望每轮只追加一条消息、读取最近若干条，则可以使用 List：

```text
RPUSH agent:context:21 '{"role":"user","content":"查年假"}'
LTRIM agent:context:21 -40 -1
```

如果保存流式事件，则更适合 Stream：

```text
XADD agent:events:21 * type tool_called tool_name knowledge_search
XREAD COUNT 50 STREAMS agent:events:21 0-0
```

需要注意，当前项目还没有把完整 Agent 对话上下文专门放进 Redis；会话消息和最终答案仍以 PostgreSQL 为持久化来源。当前 Redis 主要用于可选的短期 Agent 事件流，事件过期后通过 gap 和最终答案/持久化状态恢复，不能把 Redis 当作唯一事实来源。

标准面试回答：

> Redis 常见数据结构包括 String、List、Hash、Set、Sorted Set 和 Stream。Agent 场景中需要根据数据特点选择：完整的短期上下文快照可以用 String 保存 JSON，按消息追加并读取最近窗口可以用 List，运行状态和租约使用 Hash，流式 Agent 事件使用 Stream。Redis 适合做缓存和短期事件传递，但最终会话、最终答案和任务状态仍需要持久化到 PostgreSQL，不能只依赖 Redis，因为 Redis 数据可能过期或丢失。

#### 第 5 题补充：WeKnora 与 DeerFlow 是怎么做的

两者的共同原则是：

```text
数据库 / Checkpoint → 保存可恢复的事实
Redis / Stream      → 保存正在发生的过程，服务 SSE 和断线重连
```

### WeKnora

1. PostgreSQL 保存会话、用户消息和助手最终消息。助手消息上的 `AgentSteps` 是 JSONB，主要用于刷新页面后展示工具调用轨迹，不会把整份步骤原样当成下一轮 LLM 上下文。
2. 一次回答产生的过程事件写入 Redis。当前实现名叫 `RedisStreamManager`，实际使用的是 Redis List：

```text
stream:events:{session_id}:{message_id}
  0 → run_started
  1 → tool_called
  2 → tool_finished
  3 → message_delta
  4 → run_finished
```

追加使用 `RPUSH`，读取使用 `LRANGE`，前端用整数 offset 表示已经读到哪里；默认有 TTL（通常 24 小时）。所以它是“这次回答的事件回放缓存”，不是永久会话数据库。
3. WeKnora 还使用 Asynq + Redis 承担文档解析、摘要、知识图谱等后台任务队列。这个 Redis 队列和聊天 SSE 事件列表是两种用途，不能混为一谈。

一次问答可以理解为：

```text
用户问题 → PostgreSQL messages
        → Agent 执行工具
        → Redis List 追加过程事件
        → SSE 把事件发给浏览器
        → 最终答案和 AgentSteps 回写 PostgreSQL
```

### DeerFlow

DeerFlow 的分层更完整：

1. LangGraph 的 ThreadState + Checkpointer 保存 Agent 的可恢复执行状态，例如消息、工具调用结果、当前节点和 channel version。它是 Worker 崩溃后继续执行的依据，具体存储可以按部署配置为 SQLite/PostgreSQL 等，不把 Redis 当唯一事实来源。
2. `StreamBridge` 负责把 Worker 产生的事件送给 SSE。它可以是进程内内存桥，也可以是 Redis Stream 桥；Redis 模式用于多个进程/多个实例之间传递事件。
3. StreamBridge 只保留有界的近期事件，并支持 `Last-Event-ID`。如果浏览器要从很旧的位置恢复，但事件已经过期，就返回 `gap`；前端随后读取持久化的线程/运行状态或最终答案。Redis 的 TTL 是防止垃圾长期残留，不是 Agent 的执行超时。
4. DeerFlow 的长任务还有 RunStore、租约和心跳；Worker 崩溃后由恢复逻辑依据数据库状态接管。上下文接近 token 上限时，摘要中间件保留最近消息、总结旧消息，并把新的摘要写入 Checkpoint。

DeerFlow 的一次问答可以理解为：

```text
用户问题 → ThreadState / Checkpoint 持久化
        → Worker 执行 Agent
        → StreamBridge 发布 reasoning/tool/message 事件
        → SSE 发送给浏览器
        → 工具边界和关键状态写入 Checkpoint
        → 最终状态写入 RunStore / Checkpoint
```

### 两者的核心差异

| 对比项 | WeKnora | DeerFlow |
| --- | --- | --- |
| 聊天事件结构 | Redis List + 整数 offset | StreamBridge，支持事件 ID、游标和 gap |
| 事件用途 | 单次回答的 SSE 与回放 | 分布式 SSE、断线恢复与运行中事件桥接 |
| 最终事实 | PostgreSQL 的 messages / AgentSteps | ThreadState / LangGraph Checkpoint + RunStore |
| Agent 崩溃恢复 | 主要依赖持久化消息和后台任务机制 | 依赖 Checkpoint、租约、心跳和 orphan recovery |
| 上下文压缩 | 通过会话历史配置控制上下文 | 摘要中间件生成新 Checkpoint，保留最近消息 |

一句话区分：WeKnora 更像“数据库消息 + Redis 事件列表”；DeerFlow 更像“可恢复的 Agent 状态机 + Redis/内存事件桥”。两者都不会把 Redis 中的短期事件当作唯一的会话上下文。

本项目当前处于两者的结合形态：PostgreSQL 保存 `agent_runs`、消息和 Checkpoint；可选 Redis 保存有 TTL/长度上限的 Agent 事件；SSE 优先读取事件流，事件丢失后依靠持久化运行状态和最终答案恢复。当前没有单独的 Redis 对话上下文缓存，因此不要把 `agent:context:{run_id}` 当成已经落地的现有表或 Key。

### 结合本项目的面试标准回答

> Redis 常见的数据结构有 String、List、Hash、Set、Sorted Set 和 Stream。我的 Agent + RAG 项目中没有把所有数据都放到 Redis，而是按数据生命周期分层。
>
> PostgreSQL 是持久化来源，保存会话消息、`agent_runs`、Worker 尝试次数、租约、最终回答和 Agent Checkpoint。这样 Worker 崩溃或 Redis 事件过期后，系统仍然能够恢复任务状态和最终结果。
>
> 对于一次 Agent 回答过程，我会产生 `run_started`、`tool_called`、`tool_finished`、`message_delta`、`run_finished` 等事件。Hub 负责当前进程内的实时广播；如果配置了 Redis，则使用 Redis Stream 保存一段有 TTL 和长度上限的事件窗口，SSE 可以按事件 ID 和 `Last-Event-ID` 进行重连。Redis 在这里是短期事件传输和回放，不是最终答案的唯一来源。
>
> 如果要做完整上下文缓存，整份 JSON 快照适合用 String，按消息追加可以用 List，运行状态和租约适合用 Hash，带游标的事件日志适合用 Stream。但在当前项目里，我没有额外维护一份 Redis 对话上下文副本，而是每次从 PostgreSQL 消息、用户记忆、RAG 引用和 Checkpoint 组装模型上下文，并在内存中执行当前这一轮。这样可以避免数据库和缓存之间出现不一致。
>
> 这个设计借鉴了 WeKnora 的“数据库保存消息、Redis 保存短期事件”思路，也吸收了 DeerFlow 的 Checkpoint、事件游标和 Worker 恢复机制。核心取舍是：Redis 追求实时性，PostgreSQL 和 Checkpoint 追求可恢复性。

面试时如果被追问“为什么不用 Redis 保存全部上下文”，可以补充：Redis 可能因为 TTL、内存淘汰、服务重启或网络故障丢失数据；而 Agent 上下文、最终答案和任务状态需要可靠恢复，所以 Redis 只能作为缓存或事件层，不能替代持久化存储。

### 第 5 题补充：数据库、Redis 与对象存储的权衡

判断标准不是“Redis 快、数据库慢”，而是先问：

> 这份数据丢失后，能不能通过其他数据重新构建？

不能重建的数据放 PostgreSQL；能丢失、能重算、只为实时体验服务的数据放 Redis；体积很大的原始内容放对象存储或文件系统。

| 数据 | 推荐位置 | 原因 |
| --- | --- | --- |
| 用户、知识库、文档、Chunk、Embedding 元数据 | PostgreSQL / 向量库 | 是知识库事实，不能因为缓存过期而丢失 |
| 用户问题、助手最终回答、引用 | PostgreSQL | 用户历史和审计需要可靠保存 |
| `agent_runs`、尝试次数、租约、错误、最终状态 | PostgreSQL | Worker 接管和恢复必须有可靠来源 |
| Agent Checkpoint | PostgreSQL，过大的 payload 放对象存储 | 崩溃恢复依赖；大结果不应一直堆在数据库行或内存里 |
| `run_started`、`tool_called`、`tool_finished`、`message_delta` | Redis Stream | 只服务实时 SSE 和短期重连，设置 TTL / MAXLEN |
| 最终状态、关键工具元数据 | PostgreSQL | 即使 Redis 事件过期，也能重建运行结果 |
| 限流计数、短期幂等 Key、热点检索结果 | Redis String / Hash / Set | 有效期短，失效后可以重新计算 |
| 上传 PDF、图片、大型工具结果 | 对象存储 / 本地文件 | 避免 PostgreSQL 和 Worker 内存被大内容撑大 |

Redis 自己也可以用 RDB 或 AOF 持久化，但这不等于它天然适合替代主数据库：RDB 可能丢失最近一个快照周期的数据，AOF 也要在写入性能和 fsync 安全性之间取舍。Redis 官方也把“无持久化”列为缓存场景的选项；PostgreSQL 的事务则可以把多步更新作为一个全有或全无的提交单元。

### 对本项目的最终建议

```text
PostgreSQL
  ├── conversations / messages
  ├── agent_runs / attempts
  ├── agent_run_checkpoints
  ├── 最终答案 / 引用 / 关键运行事件
  └── 文档、Chunk、评测结果

Redis
  ├── Hub 的跨进程事件桥：Redis Stream
  ├── 短期 SSE 回放窗口
  ├── 限流、短期缓存、幂等标记
  └── 不保存唯一的会话事实和最终答案

对象存储 / 文件系统
  ├── 原始 PDF、DOCX、图片
  ├── 超大的工具结果
  └── 超大的 Checkpoint payload
```

不要把所有流式事件写入 PostgreSQL：`message_delta` 可能每几十个字符产生一次，会造成大量写放大。可以只把 `run_started`、工具调用摘要、工具完成摘要、错误、最终状态写入数据库；完整的短期过程仍由 Redis Stream 提供。SSE 不应使用 Redis Consumer Group，因为多个浏览器连接需要各自看到完整事件；它们应使用独立的事件 ID 游标。Consumer Group 更适合多个 Worker 分摊后台任务。

这套方案与 WeKnora 的“消息进 PostgreSQL、事件进 Redis”一致，也吸收了 DeerFlow 的做法：Redis StreamBridge 负责跨实例 SSE 和有限回放窗口，Checkpoint / RunStore 负责持久化恢复；当事件窗口已经裁剪时，通过 `gap` 让前端重新加载持久化状态，而不是把 Redis 当作唯一事实来源。

### 第 5 题补充：Redis 与 PostgreSQL 是否可以同时保存同一份数据

可以，但应明确是“PostgreSQL 主存储 + Redis 缓存”，而不是两个平等的数据源。推荐读取流程：

```text
先读 Redis
  ├── 命中且版本有效 → 直接返回
  └── 未命中 / 已过期
        ↓
      读取 PostgreSQL
        ↓
      回填 Redis，并设置 TTL
        ↓
      返回结果
```

推荐写入流程：

```text
PostgreSQL 事务提交成功
        ↓
删除或更新 Redis 缓存
        ↓
下次读取时重新回填
```

不建议直接“同时写两边然后认为一定一致”，因为会出现：

1. PostgreSQL 写成功、Redis 写失败：两边暂时不一致；
2. Redis 写成功、PostgreSQL 写失败：Redis 可能返回一个数据库中不存在的数据；
3. 更新并发交错：旧请求晚到，可能把旧数据重新写回 Redis；
4. Redis 过期、重启或被淘汰：缓存突然全部消失，数据库必须能承受回源流量；
5. 多个 Worker 同时回源：同一个 Key 同时查询数据库，造成缓存击穿；
6. 没有版本号或租户隔离：旧版本数据或其他用户数据可能被错误复用。

因此缓存值最好带上版本或更新时间，并使用 TTL。对高并发热点 Key，还需要 singleflight、短暂分布式锁或随机 TTL，避免大量 Worker 同时回源。

放到本项目中：最终答案、会话消息、`agent_runs` 和 Checkpoint 可以增加 Redis 热点缓存，但 PostgreSQL 仍是唯一事实来源；写入时先提交 PostgreSQL，再删除或异步更新 Redis。SSE 事件则不建议同时把每个 `message_delta` 写 PostgreSQL，因为写放大很严重；Redis 保存短期事件，数据库只保存最终答案、Checkpoint 和必要的工具摘要即可。

如果未来要求“数据库记录和 Redis 缓存必须最终一致”，可以在同一个 PostgreSQL 事务中同时写业务表和 outbox 表，再由后台 Worker 消费 outbox 更新 Redis。这样 Redis 更新失败可以重试，但仍然要接受短暂的最终一致性，不能假设两个系统具有原子提交。

### 第 5 题补充：为什么当前最适合 Redis 的是 SSE 事件

你的判断基本正确：当前 Agent + RAG 对话没有明显的高频热点上下文。

```text
单轮对话：
Worker 内存保存本轮临时上下文
大型工具结果保存临时文件
Checkpoint 保存可恢复的状态和文件引用

多轮对话：
每轮从 PostgreSQL 读取历史消息、用户记忆和必要引用
重新组装当前模型上下文

实时展示：
Worker 发布事件
  ↓
Hub / Redis Stream
  ↓
SSE Handler
  ↓
浏览器
```

多轮消息虽然可能比较大，但访问频率通常远低于 `message_delta` 事件，而且消息是必须长期保留的事实数据，直接从 PostgreSQL 读取更简单，也避免维护一份 Redis 上下文副本。

因此当前项目中 Redis 的首要用途是：

- 跨 Worker / 跨进程传递 Agent 事件；
- 支持 SSE 断线后的短期回放；
- 通过事件 ID 判断是否出现 gap；
- 把实时事件和最终答案、Checkpoint 解耦。

如果只有单进程、SSE 连接也不会跨实例，那么进程内 Hub 就可以完成实时广播，Redis 甚至可以关闭。部署多个 Worker、允许请求和执行任务落在不同进程，或者需要短期断线恢复时，Redis Stream 才真正体现价值。

还要注意：大型工具结果放临时文件并不代表完全不需要持久化。Checkpoint 至少要保存文件路径或对象存储 Key、文件大小、校验值、工具名和参数摘要；否则 Worker 接管后不知道去哪里取结果。临时文件本身可以在任务终止后清理，真正需要长期保留的文件才进入对象存储。

#### 新面试题：什么是 Reranker，以及 WeKnora 如何使用

Reranker（重排模型）不是负责从整个知识库找候选，而是对第一阶段已经召回的少量候选重新判断相关性。典型链路是：

```text
全库
  ↓
向量召回 / 关键词召回 / 图谱召回
  ↓
得到几十条候选
  ↓
RRF 融合、去重
  ↓
Reranker 对 query + passage 成对判断
  ↓
返回最相关的 5～10 条
  ↓
交给回答模型生成答案
```

Embedding 通常是“问题向量”和“Chunk 向量”分别编码后计算相似度；Reranker 则同时看到问题和候选正文，可以更准确地判断否定、条件、数字和上下文关系。因此它通常更准，但计算更慢、成本更高，所以只对召回候选做第二阶段排序，不直接对全库调用。

WeKnora 的 `knowledge_search` 先并发执行配置好的多路检索，再用 RRF 融合排名，随后在调用 Rerank 前去重。配置了专用 Rerank 模型时，向模型传入查询和候选 passage；专用模型失败或没有结果时，可以回退到聊天模型做 LLM 重排；两者都没有配置时，直接使用融合后的结果。Rerank 后还会用阈值过滤，再通过 MMR 减少重复 Chunk，最后排序并返回有限结果。

例如用户问“年假怎么计算”：

```text
RRF 初始顺序：
1. 年假申请流程
2. 员工福利与年假制度
3. 年假按入职年限计算

Rerank 分数：
1. 0.42
2. 0.71
3. 0.96

最终顺序：
1. 年假按入职年限计算
2. 员工福利与年假制度
3. 年假申请流程
```

当前项目的检索服务也采用同样的边界：向量检索和关键词检索先合并并用 RRF 融合，Reranker 只接收扩大的候选集，再输出最终 Top-K；没有配置 Reranker 时保留 RRF 结果。Rerank 调用失败不会让整个知识库问答失败，而是记录 fallback 并退回融合结果。项目还记录 `rerank_before`、`rerank_after` 和 `rerank_fallback`，便于评测质量和成本。

面试标准回答：

> Reranker 是 RAG 的第二阶段排序模型。第一阶段使用向量、关键词或图谱召回，目标是保证召回率；第二阶段把用户问题和候选 Chunk 一起交给 Cross-Encoder 或专用重排模型，目标是提高 Top-K 的精确率。我的项目先进行 Hybrid RAG 和 RRF 融合，再对去重后的候选执行可选 Rerank，最后进行 MMR 去冗余。如果 Rerank 服务没有配置或调用失败，则回退到 RRF 结果，不影响主流程。这样兼顾了召回覆盖率、最终上下文质量、延迟和成本。

#### Rerank 后的 MMR 是什么

MMR（Maximal Marginal Relevance，最大边际相关性）用于在“和问题相关”和“不要与已选内容重复”之间做平衡。它不是再次从全库检索，也不是简单按文档 ID 去重，而是在每选择一个 Chunk 时，重新计算它的边际价值。

常见公式是：

```text
MMR(d) = λ × Sim(d, query)
         - (1 - λ) × max Sim(d, selected_chunk)
```

其中：

- `Sim(d, query)`：候选 Chunk 和问题的相关性；
- `Sim(d, selected_chunk)`：候选 Chunk 和已经选中 Chunk 的相似度；
- `λ`：相关性和多样性的权重，越大越偏向相关性，越小越强调多样性。

例如 Rerank 后有三个候选：

```text
A：年假按工龄计算，相关性 0.95
B：年假按累计工龄计算，相关性 0.92，与 A 的相似度 0.95
C：年假申请流程，相关性 0.85，与 A 的相似度 0.20
```

先选 A。第二轮虽然 B 的相关性高于 C，但 B 和 A 几乎重复，重复惩罚后可能变成：

```text
B 的 MMR = 0.7 × 0.92 - 0.3 × 0.95 = 0.359
C 的 MMR = 0.7 × 0.85 - 0.3 × 0.20 = 0.535
```

于是第二个选择 C。最终上下文同时包含“计算规则”和“申请流程”，而不是把同一规则的相似 Chunk 全部塞给回答模型。WeKnora 的检索工具在 Rerank 后使用 MMR；当前实现使用 `lambda=0.7`，偏向相关性，同时保留一定多样性。

一句话：Rerank 解决“谁最相关”，MMR 解决“在相关的结果里，怎样少重复、覆盖更多信息”。MMR 不会提高全库召回率，它主要优化最终 Top-K 上下文的有效信息密度。

#### 第 6 题：线程池的参数如何设置

用户回答：

> Go 里面没有线程池这个说法，Go 语言使用比线程更轻量的协程进行调度和工作，底层会实现类似线程池的机制，对协程进行回收和再发放。在项目中体现在 Worker 的设置，Worker 设置为 5 个。

评价：方向基本正确，可以得到基础分。需要修正的是：Go 的 goroutine 不是传统意义上由线程池回收再发放的对象。Go Runtime 使用 G-M-P 调度模型，让大量 goroutine 复用少量操作系统线程；goroutine 执行结束后退出，其栈由运行时和 GC 管理。真正固定“并发槽位”的 Worker 池，通常是应用自己创建固定数量的 goroutine，让它们循环从任务队列领取任务。

```text
任务队列
  ├── Worker goroutine 1
  ├── Worker goroutine 2
  ├── Worker goroutine 3
  ├── Worker goroutine 4
  └── Worker goroutine 5
```

设置 Worker 数量不能只凭经验，需要看任务类型：

- CPU 密集型：并发数通常接近 CPU 核数，过多会增加上下文切换；
- IO 密集型：可以高于 CPU 核数，但要受数据库连接、模型 API 限流和内存约束；
- Agent 任务：通常是 IO 等待较多，但每个任务又可能占用较大的上下文和工具资源，不能无限增加；
- 子 Agent：应使用共享调度器限制总并发，不能让每个父 Agent 各自创建 5 个槽位。

结合当前源码需要区分：`DOCUMENT_WORKER_CONCURRENCY` 控制的是文档处理 Worker，不是 Agent Run Worker。Agent Run 现在通过 `AGENT_WORKER_CONCURRENCY` 启动共享 Worker 池；例如配置为 5，才代表一个进程最多同时处理 5 个 Agent Run。默认值仍为 1，避免没有评估下游容量时突然放大模型并发。

面试标准回答：

> Go 没有 Java 那种显式线程池，主要使用 goroutine 和 channel。Go Runtime 通过 G-M-P 调度模型把大量 goroutine 调度到少量 OS 线程上。工程上如果需要限制任务并发，通常会创建固定数量的 Worker goroutine，让它们从任务队列中循环领取任务。参数设置要根据任务类型决定：CPU 密集型接近 CPU 核数，IO 密集型可以适当提高，但还要受数据库连接池、外部 API 限流、内存和下游服务容量约束。当前项目的 Agent Runner 是一个后台循环，每次领取并执行一个 Agent Run；如果未来扩展为多个 Agent Runner，应让它们共享数据库的 `ClaimNext` 领取机制，并统一限制总并发。父 Agent 创建的子 Agent 也应使用同一套调度边界。

#### 新面试题：介绍 SSE，以及项目中如何使用

SSE（Server-Sent Events）是一种基于 HTTP 的服务器单向推送技术。浏览器发起一个长连接请求，服务器持续返回 `text/event-stream` 格式的事件，直到任务完成、失败、取消或连接断开。它的方向是：

```text
浏览器 ──普通 HTTP 请求──> 服务器
浏览器 <──SSE 事件────── 服务器
```

一个 SSE 事件大致长这样：

```text
id: event-12
event: tool_finished
data: {"tool":"knowledge_search","count":5}

```

事件之间用空行分隔。`id` 用于断线恢复，`event` 表示事件类型，`data` 携带 JSON 数据。SSE 只负责服务器到浏览器的实时推送；提交问题、停止任务等操作仍然使用普通的 POST 请求。相比 WebSocket，SSE 协议更简单，适合 Agent 的“后端持续输出、前端主要接收”场景。

在本项目的持久化 Worker 模式下，流程是：

```text
POST /api/knowledge-bases/{id}/agent-chat/stream
  → 创建 agent_run，返回 run_id / stream_url
  → Worker 从数据库领取任务
  → Worker 执行 Agent 并发布事件
  → Hub 负责当前进程内广播
  → Redis Stream 或 PostgreSQL EventStore 负责回放
  → GET /api/knowledge-bases/{id}/agent-runs/{runID}/stream
  → SSE Handler 持续写给浏览器
  → 最终答案和运行状态保存到 PostgreSQL
```

例如用户问“年假怎么计算”：

```text
run_started
tool_called: knowledge_search
tool_finished: 找到 5 个 Chunk
message_delta: 年假根据……
run_finished
```

这些事件先由 Worker 产生，SSE Handler 再负责转成 SSE 帧。Worker 不需要一直占用浏览器的 HTTP 请求；即使浏览器刷新，任务也可以继续执行。用户主动停止时，才通过 stop 接口取消对应的 Agent context。

浏览器重连时会携带 `Last-Event-ID: event-12`。后端尝试从 Hub 或 Redis 的保留窗口中读取 `event-12` 之后的事件；如果事件还在，就继续推送。如果事件已经过期，返回 `gap`，前端改为读取 PostgreSQL 中的运行状态、最终答案和 Checkpoint 进行恢复。Redis 事件是实时过程，数据库和 Checkpoint 才是最终恢复依据。

结合本项目的标准回答：

> SSE 是基于 HTTP 的服务器单向推送协议，浏览器建立一个 `text/event-stream` 长连接，服务器可以持续发送带有 `id`、事件类型和 JSON 数据的消息。我的 Agent + RAG 项目中，用户先通过 POST 创建 `agent_run`，后台 Worker 异步执行 Agent；Worker 产生 `run_started`、工具调用、工具结果、回答增量和结束事件。Hub 负责进程内广播，配置 Redis 后由 Redis Stream 提供跨进程传输和短期回放，SSE Handler 将这些事件推送给前端。浏览器重连时通过 `Last-Event-ID` 请求后续事件；如果事件已经过期，就通过 `gap` 触发前端读取 PostgreSQL 中的最终答案和 Checkpoint。这样实时展示和任务持久化是解耦的，SSE 断开不会导致 Agent 任务本身停止。

#### SSE 最小 Go 实现对应关系

最小实现可以只有一个内存事件通道：

```go
type Event struct {
    ID, Type, Data string
}

type Run struct {
    ID     string
    Events chan Event
}

var runs sync.Map // runID -> *Run

func submit(w http.ResponseWriter, r *http.Request) {
    run := &Run{
        ID:     fmt.Sprintf("run-%d", time.Now().UnixNano()),
        Events: make(chan Event, 16),
    }
    runs.Store(run.ID, run)

    go func() {
        defer close(run.Events)
        emit := func(id, typ, data string) {
            run.Events <- Event{ID: id, Type: typ, Data: data}
        }
        emit("1", "run_started", `{}`)
        emit("2", "tool_called", `{"tool":"knowledge_search"}`)
        emit("3", "tool_finished", `{"count":5}`)
        emit("4", "message_delta", `{"text":"根据知识库资料，年假……"}`)
        emit("5", "run_finished", `{"answer":"年假根据入职年限计算"}`)
    }()

    w.WriteHeader(http.StatusAccepted)
    json.NewEncoder(w).Encode(map[string]string{
        "run_id":     run.ID,
        "stream_url": "/runs/" + run.ID + "/stream",
    })
}

func stream(w http.ResponseWriter, r *http.Request) {
    runID := strings.TrimPrefix(r.URL.Path, "/runs/")
    value, ok := runs.Load(runID)
    if !ok {
        http.NotFound(w, r)
        return
    }
    run := value.(*Run)

    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    flusher := w.(http.Flusher)

    for {
        select {
        case event, ok := <-run.Events:
            if !ok {
                return
            }
            fmt.Fprintf(w, "id: %s\nevent: %s\ndata: %s\n\n",
                event.ID, event.Type, event.Data)
            flusher.Flush()
        case <-r.Context().Done():
            return // 浏览器断开，不代表 Worker 停止
        }
    }
}
```

这个示例中的对应关系是：`submit` 相当于创建 `agent_run`，goroutine 相当于 Worker，`run.Events` 相当于进程内 Hub，`stream` 相当于 SSE Handler。真实项目中，`run.Events` 不能承担跨进程和断线回放，因此替换为 Hub + Redis Stream；最终答案和任务状态则写 PostgreSQL。

#### 第 6 题补充：多个用户同时访问时，goroutine、线程和 Worker 的关系

启动一个 Go 后端进程后，不是每个用户对应一个固定线程，而是：

```text
一个 Go 进程
  ├── HTTP Server
  ├── 用户 A 的请求 goroutine
  ├── 用户 B 的请求 goroutine
  ├── 用户 C 的 SSE goroutine
  ├── Agent Runner goroutine
  └── 当前 Agent Run 的心跳 goroutine
```

Go 的 HTTP Server 通常会为每个请求分配 goroutine。goroutine 是用户请求的执行单元，Worker 是应用层限制 Agent 任务并发的执行槽位，两者不是同一个概念。Go Runtime 再把这些 goroutine 调度到少量 OS 线程上。

三个用户同时提问时，持久化 Agent 模式大致是：

```text
t0：A、B、C 同时 POST
    A → agent_runs: pending
    B → agent_runs: pending
    C → agent_runs: pending
    三个 HTTP 请求很快都返回 202 和 run_id

t1：共享 Agent Worker 池中的 Worker 1/2/3 分别领取 A/B/C
    A、B、C → running
    三个 Run 同时调用模型和工具，各自启动心跳 goroutine

t2：A、B、C 都建立 SSE
    A 的 SSE 收到 A 的工具事件
    B、C 的 SSE 暂时等待各自的事件

t3：A 执行完成
    A → succeeded
    Worker 1 继续领取下一个 pending Run

t4：B、C 按各自执行速度独立完成，互不阻塞
```

当前项目通过 `AGENT_WORKER_CONCURRENCY` 启动共享 Agent Worker 池。例如配置为 3：

```go
agentRunRunner.RunWorkers(ctx, 3, pollInterval, report)
```

那么可以变成：

```text
Worker 1 → A
Worker 2 → B
Worker 3 → C
```

它们共同调用数据库的 `ClaimNext`，通过事务锁和 `FOR UPDATE SKIP LOCKED` 确保两个 Worker 不会领取同一条 Run。每个 Worker 领取一条 Run 后，自己的执行路径调用 Agent，额外启动一个心跳 goroutine；因此 3 个 Worker 不代表进程里只有 3 个 goroutine。

最小结构可以写成：

```go
func submit(w http.ResponseWriter, r *http.Request) {
    // HTTP Server 已经为这个请求提供了 goroutine
    run := store.CreatePendingRun(r.Context())
    json.NewEncoder(w).Encode(run)
}

func workerLoop(ctx context.Context) {
    for {
        run, err := store.ClaimNext(ctx)
        if err == ErrNoRun {
            time.Sleep(time.Second)
            continue
        }

        executionCtx, cancel := context.WithCancel(ctx)
        go renewLease(executionCtx, run) // 辅助 goroutine
        executeAgent(executionCtx, run)  // 主执行路径
        cancel()
    }
}
```

这个例子体现了三个边界：HTTP goroutine 负责接收请求，Worker 负责控制昂贵 Agent 执行的并发，OS 线程由 Go Runtime 统一调度。用户数量增加时，轻量的 POST 和 SSE 请求可以很多；真正需要根据 CPU、模型 API、数据库连接和内存限制的是 Agent Worker 数量。

#### 第 6 题补充：Worker A 崩溃后，Worker B 如何接管

Worker A 和 Worker B 没有主备角色，它们运行相同的程序、连接相同的 PostgreSQL，并各自启动一个 `Runner` 循环。A 领取任务后，数据库记录：

```text
status       = running
attempt_count = 1
lease_token  = token-a
lease_until  = 10:05:00
heartbeat_at = 10:00:00
```

A 执行 Agent 时，主执行路径调用模型和工具；心跳 goroutine 定期使用 `lease_token` 更新 `lease_until`。如果 A 进程崩溃，心跳停止，但数据库不会立刻知道 A 崩溃，而是等到 `lease_until` 到期。

B 启动时会执行与 A 相同的初始化：创建数据库 Store、Agent Executor、EventStore 和 Runner，然后启动：

```go
agentRunRunner.RunWorkers(runContext, cfg.AgentWorkerConcurrency, pollInterval, report)
```

每次 Runner 循环大致做两步：

```go
func (r *Runner) RunOnce(ctx context.Context) {
    r.store.RequeueExpired(ctx) // 先恢复过期租约
    run, err := r.store.ClaimNext(ctx)
    if err != nil {
        return
    }
    r.execute(run)
}
```

`RequeueExpired` 查找 `status = 'running'` 且 `lease_until <= now()` 的任务：

```text
未超过最大尝试次数：running → pending
达到最大尝试次数：running → failed
```

然后 B 的 `ClaimNext` 使用数据库事务和 `FOR UPDATE SKIP LOCKED` 领取待处理任务：

```text
pending
  ↓ ClaimNext
running + 新 lease_token
  ↓ 读取 Checkpoint
继续执行 Agent
```

B 不会直接相信 A 已经执行到哪一步，而是读取 A 已经保存的安全工具 Checkpoint 和模型决策 Checkpoint。能够证明参数一致、工具是只读且结果完整时，可以复用已经完成的工具结果，减少重复调用；无法证明安全时就重新执行。

需要注意，A 的进程内 Hub 会随着进程崩溃而消失。前端 SSE 连接会断开并重连到 B；如果 Redis 事件还在保留窗口中，就从事件 ID 后继续读取；如果事件已经过期，就通过 `gap` 读取 PostgreSQL 中的运行状态、Checkpoint 和最终答案。A、B 的执行接管依赖 PostgreSQL，SSE 的实时过程恢复依赖 Hub/Redis，两者是不同问题。

当前源码中，Agent Runner 实际是单个后台循环；所以一个进程一次执行一个顶层 Agent Run。启动多个相同进程后，才会出现 A、B 同时处理不同 Run 的并发，数据库领取逻辑负责避免重复领取。`DOCUMENT_WORKER_CONCURRENCY` 控制的是文档 Worker，不是 Agent Run Worker。

#### 第 6 题补充：为什么说 Worker B 接手，而不是直接重新创建 Worker A

这里的 A、B 只是不同时间或不同进程中的 Worker 实例，不是系统里预先固定的两个角色：

```text
Worker A 进程崩溃
  ↓
进程管理器 / Docker / Kubernetes 重启同一份程序
  ↓
新的 Runner 实例
  ↓
它在任务语义上就是 Worker B
```

即使把它叫作“重新创建 Worker A”，本质上也是一个新的进程。新进程必须知道数据库里哪些任务仍然是 `running`、哪些租约已经过期、是否可以重试；因此仍然需要租约和 `RequeueExpired`。如果 A 不是崩溃，而是卡死但进程仍然存在，单纯“重新创建 A”也不会自动发生，租约过期检测才能让其他 Worker 发现它没有继续心跳。

最小的内存版 Worker 可以这样写：

```go
type Task struct {
    ID      string
    Payload string
}

type Worker struct {
    ID    string
    Tasks <-chan Task
}

func (w *Worker) Run(ctx context.Context) {
    for {
        select {
        case task := <-w.Tasks:
            fmt.Println(w.ID, "执行", task.ID)
            doWork(ctx, task)
        case <-ctx.Done():
            return
        }
    }
}

func main() {
    tasks := make(chan Task, 10)
    worker := &Worker{ID: "worker-a", Tasks: tasks}

    go worker.Run(context.Background())
    tasks <- Task{ID: "run-1", Payload: "查询年假"}
}
```

这个版本中，任务只在 Channel 内存里。Worker 崩溃后，任务和执行位置都会丢失，重新创建 Worker 也不知道 `run-1` 是否执行过，因此它只适合教学演示。

真实项目把任务放数据库：

```go
func (r *Runner) Run(ctx context.Context) {
    for {
        r.store.RequeueExpired(ctx)

        run, err := r.store.ClaimNext(ctx)
        if err == ErrNoRun {
            time.Sleep(time.Second)
            continue
        }
        if err != nil {
            continue
        }

        executionCtx, cancel := context.WithCancel(ctx)
        go r.renewLease(executionCtx, run)

        err = r.executor.Execute(executionCtx, run, r.publishEvent)
        cancel()

        if err == nil {
            r.store.MarkSucceeded(ctx, run.ID, run.LeaseToken)
        } else {
            r.store.MarkFailed(ctx, run.ID, err.Error(), run.LeaseToken)
        }
    }
}
```

此时 Worker 的身份是临时的，但任务状态是持久的：

```text
Worker A 领取 run-1
  → running + token-a
  → 执行过程中崩溃

新 Worker B 启动
  → 发现 token-a 的 lease 已过期
  → running → pending
  → 使用 token-b 重新 ClaimNext
  → 读取 Checkpoint
  → 继续执行
```

所以接管机制解决的不是“如何创建 goroutine”，而是“Worker 消失后，任务如何被可靠发现、重新领取和恢复”。当前项目只启动一个 Agent Runner 时，A 崩溃后必须先由外部进程管理器拉起新服务；如果已经有多个服务实例，其他实例可以直接充当 B，不需要等待 A 所在进程重启。

#### 第 6 题补充：当前 Worker 设计的优点与缺口

当前设计已经完成同一进程内的 Worker 并发；多用户的独立请求会生成独立 Run，并由共享队列分配。跨进程接管仍依赖服务实例重启或多实例部署，但不需要给 Worker 分配固定的用户或任务。

已经正确的部分：

- 任务状态、租约和尝试次数在 PostgreSQL 中保存；
- `ClaimNext` 使用 `FOR UPDATE SKIP LOCKED`，避免重复领取；
- 心跳失败后，租约会过期；
- 新 Runner 可以通过 `RequeueExpired` 恢复任务；
- Checkpoint 可以减少接管后的重复工具调用和模型决策。

使用时仍要同步检查数据库连接池、模型 API 并发限制、内存和工具幂等性，避免只调大 Worker 数量就把下游资源压垮。账号登录与资源级隔离是独立的多租户问题；本项目现有 app_users/session 目前主要服务用户记忆，知识库仍按本地管理员范围管理，不能把“并发多用户”误称为完整 RBAC 多租户。

### 第 7 题：2PC、TCC 与 Agent 跨系统一致性

#### 我的回答

不会。

#### 知识点

**2PC（Two-Phase Commit，两阶段提交）**由协调者统一控制两个阶段：

1. Prepare：协调者询问所有参与者能否提交，参与者预留资源并回复成功或失败；
2. Commit/Rollback：所有参与者都准备成功时统一提交，否则统一回滚。

优点是业务方不需要自己设计补偿逻辑；缺点是协调者、锁和网络故障会让参与者长时间阻塞，吞吐量和可用性也会下降。

**TCC（Try-Confirm-Cancel）**把业务操作拆成三个接口：

1. Try：检查条件并预留资源；
2. Confirm：正式提交；
3. Cancel：释放预留资源或执行业务补偿。

例如 Agent 执行“扣库存并创建订单”：Try 阶段先冻结库存，所有系统都成功后 Confirm；如果订单创建失败，就调用 Cancel 解冻库存。TCC 的优点是可用性更好，缺点是每个有副作用的工具都必须提供可靠、幂等的 Confirm/Cancel。

#### 结合本项目的标准答案

在 Agent 执行跨系统指令时，我不会把模型调用本身放进 2PC。模型调用通常耗时长、不可回滚，也不适合持有数据库事务。我的做法是：

```text
Agent Run 持久化步骤状态
  ↓
调用普通只读工具：失败可重试
  ↓
调用有副作用工具：先审批，再执行
  ↓
每个步骤保存 operation_id 和执行状态
  ↓
失败时按工具提供的补偿动作回滚，或进入人工处理
```

工程上更接近 **Saga/补偿事务**：每一步独立提交，失败后调用前面步骤的补偿操作。无论采用 2PC、TCC 还是 Saga，工具都必须保证幂等，例如使用 `operation_id` 防止 Worker 重试时重复扣款或重复创建订单。

因此可以这样回答面试官：2PC 通过协调者的 Prepare 和 Commit 保证统一提交，但会阻塞并降低可用性；TCC 通过 Try、Confirm、Cancel 让业务自己实现预留和补偿，灵活性更高。Agent 场景通常使用持久化状态机加 Saga 补偿，普通工具允许重试，有副作用工具需要审批、幂等键和明确的补偿策略。

### 第 8 题：如何实现类 Manus Agent 的高可用任务调度器

#### 我的回答

不会。

#### 知识点

类 Manus Agent 会频繁调用浏览器、文件系统、代码执行和外部 API，因此调度器不能只依赖内存队列。核心设计是“持久化任务状态机 + Worker 租约 + 幂等执行”。

任务表至少保存：`task_id`、`run_id`、任务状态、优先级、尝试次数、`lease_owner`、`lease_expires_at`、下一次执行时间、幂等键和错误信息。状态可以是 `pending`、`running`、`succeeded`、`failed`、`canceled`。

Worker 使用数据库事务和 `FOR UPDATE SKIP LOCKED` 领取任务，领取时写入租约和租约过期时间；执行期间由心跳续租。Worker 崩溃后，其他 Worker 通过租约过期扫描把任务重新放回 `pending`，再重新领取。

失败处理需要区分错误类型：网络抖动和临时 5xx 可以指数退避重试；参数错误应反馈给 Agent 修正；不可恢复错误进入失败或死信状态。每个任务设置最大尝试次数，并记录每次尝试的错误和耗时。

由于 Worker 可能在执行成功后、写回状态前崩溃，调度器必须接受“至少一次执行”，而不是假设“恰好一次执行”。因此工具要使用幂等键，重要步骤还要保存 checkpoint；有副作用的工具需要审批、幂等和补偿机制。

调度器还要考虑优先级、队列背压、每个用户或租户的并发上限、模型 API 限流、CPU/内存限制、超时、取消、任务依赖和监控告警。执行代码或操作环境时，应放在隔离的沙箱或容器中，限制文件系统、网络、CPU 和内存访问。

#### 结合本项目的标准答案

我的实现会让多个无状态 Worker 共同消费 PostgreSQL 中的 `agent_runs`，通过 `FOR UPDATE SKIP LOCKED` 避免重复领取；用 lease 和 heartbeat 处理 Worker 崩溃恢复，用指数退避和错误分类处理重试，用 `operation_id` 和 checkpoint 防止副作用工具重复执行。最终状态、答案和恢复信息写入 PostgreSQL，短期过程事件通过 Redis/Hub 推送给 SSE，监控记录任务耗时、尝试次数、失败原因和模型成本。

因此可以这样回答面试官：高可用 Agent 调度器的关键不是简单增加 Worker 数量，而是让任务可持久化、可租约领取、可重试、可恢复、可幂等，并且对资源、权限、依赖和执行环境进行隔离。当前项目已经具备 Agent Run、Worker 池、租约、心跳、断点恢复和 SSE；如果扩展到 Manus 类环境操作，还需要补充沙箱、资源配额和更完整的任务依赖调度。

#### 第 8 题补充：`FOR UPDATE SKIP LOCKED`

`FOR UPDATE` 会在事务中锁住被选中的任务行，避免其他 Worker 同时修改或领取同一任务；`SKIP LOCKED` 表示遇到已经被其他 Worker 锁住的任务时直接跳过，继续寻找下一条未锁定任务。

```sql
BEGIN;

SELECT id
FROM agent_runs
WHERE status = 'pending'
FOR UPDATE SKIP LOCKED
LIMIT 1;

UPDATE agent_runs
SET status = 'running',
    lease_owner = 'worker-b',
    lease_expires_at = NOW() + INTERVAL '1 minute'
WHERE id = 2;

COMMIT;
```

例如 Worker A 锁住 `run-1` 后，Worker B 查询时会跳过 `run-1`，领取 `run-2`。这样多个 Worker 可以并行消费任务，而不会因为等待同一把行锁而排队。但它只解决并发领取问题，仍需要配合租约、心跳、幂等键和 checkpoint 处理 Worker 崩溃后的重复执行风险。

### 第 9 题：MySQL 隔离级别与幻读

#### 我的回答

不会。

#### 知识点

MySQL 常见的四种事务隔离级别，从低到高是：

| 隔离级别 | 可能出现的问题 | 说明 |
| --- | --- | --- |
| Read Uncommitted | 脏读、不可重复读、幻读 | 可以读到其他事务尚未提交的数据 |
| Read Committed | 不可重复读、幻读 | 只能读到已经提交的数据 |
| Repeatable Read | InnoDB 中通过 MVCC 和间隙锁减少幻读 | 同一事务多次普通查询通常看到一致快照，InnoDB 默认级别 |
| Serializable | 基本避免并发读写问题 | 通过更强的锁把事务串行化，并发性能最低 |

**脏读**是读到了其他事务尚未提交的数据；如果对方最终回滚，刚才读到的内容就是无效数据。

**不可重复读**是同一个事务中，两次读取同一行得到不同结果，因为另一个事务在两次读取之间修改并提交了这条记录。

**幻读**不是同一行的值变了，而是同一个事务按照相同条件再次查询时，结果集中出现了之前不存在的新行，或者原来的行消失了。

例如事务 A 执行：

```sql
BEGIN;
SELECT * FROM orders WHERE user_id = 10;
-- 返回 2 条订单
```

事务 B 此时插入一条 `user_id = 10` 的订单并提交。事务 A 再次执行相同查询：

```sql
SELECT * FROM orders WHERE user_id = 10;
-- 读到了 3 条订单
```

多出来的那一条记录就像“幻影”，这就是幻读。它的本质是范围查询结果发生了变化，而不是某一条已存在记录的字段发生变化。

#### 面试标准答案

MySQL 的事务隔离级别有 Read Uncommitted、Read Committed、Repeatable Read 和 Serializable。Read Uncommitted 可能发生脏读、不可重复读和幻读；Read Committed 可以避免脏读，但仍可能不可重复读；Repeatable Read 保证同一事务中普通查询的一致性，InnoDB 还通过 MVCC 和间隙锁处理范围并发；Serializable 通过串行化事务提供最强隔离，但并发性能最低。

幻读是同一个事务中，使用相同条件进行范围查询时，前后两次结果集出现了新增或消失的记录。例如第一次查询某用户有 2 个订单，另一个事务插入并提交后，第二次查询变成 3 个订单，这就是幻读。

#### 结合 Agent 后端

Agent Worker 领取任务时不能只依赖隔离级别解决重复领取，而要使用短事务、`FOR UPDATE SKIP LOCKED`、租约和状态条件。隔离级别负责数据库事务之间如何互相看见数据；任务幂等和租约负责 Worker 崩溃、重试以及重复执行问题。

#### 第 9 题补充：MVCC 如何处理幻读

MVCC 可以让普通快照读避免“看到幻读”，但它不一定阻止其他事务插入新记录。事务 A 第一次查询范围得到 2 条记录后，事务 B 插入第 3 条并提交；事务 A 再次执行普通 `SELECT` 时，仍然读取第一次建立的快照，因此看到的还是 2 条。

```text
普通快照读       → 新记录对当前事务不可见，保证前后结果一致
SELECT FOR UPDATE → 当前读，读取最新版本，并可能加行锁/间隙锁
```

MVCC 主要解决“当前事务看不到不该看到的新版本”；间隙锁解决“其他事务不能向当前查询范围插入数据”。因此在 MySQL InnoDB 中，Repeatable Read 通常结合 MVCC 快照和 Next-Key Lock 处理幻读，不能简单把所有责任都归给 MVCC。
